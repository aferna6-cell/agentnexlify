6. Grep test files for hard-coded retired plan names:
   ```bash
   grep -rn "growth\|autopilot\|professional\|enterprise\|foundation\|operations" backend/tests/ tests/
   ```

7. Update `backend/tests/test_plan_gating_new_plans.py` — add/update `assert plan in gate` / `assert plan not in gate` lines to lock the full mapping.
8. Check `CLAUDE.md` "Plan names + prices" section — if it still lists retired names as "current", rewrite it to reflect the live model.
9. Run `bash scripts/ci-local.sh` — confirm ALL GATES PASSED.
10. Commit with message: `fix: propagate <new-plan-name> across all plan gates (#<issue>)`.

### 2. `leadgen-add-source`

**Trigger condition:** User says "add a new leadgen source", "add X as a data source for leads", "leadgen needs Y fallback", or when `scripts/leadgen/README.md` documents a gap (e.g. "Google key unavailable — add OSM fallback").

1. Read `scripts/leadgen/README.md` — understand the current pipeline: `build_leads.py` → sources (`places.py`, `osm.py`) → `enrich.py` → `merge_leads.py` → CSV.
2. Read `scripts/leadgen/build_leads.py` — understand the `--source` dispatch and the `place_dict` contract (required fields: `business_status`, `name`, `website`, `phone`, `address`, `city`, `place_id`).
3. Read an existing source (`scripts/leadgen/osm.py` or `scripts/leadgen/places.py`) — use as the implementation template.
4. Create `scripts/leadgen/<source_name>.py`:
   - Implement the same output contract (`place_dict` shape + `business_status=OPERATIONAL` so `is_usable()` passes).

5. Add `--source <name>` option to `build_leads.py`; update the `auto` fallback chain.
6. Update `scripts/leadgen/__init__.py` exports if the module exposes a public interface.

8. Update `scripts/leadgen/README.md` — add the new source to the "Sources" section with usage example, key/cost requirements, and any ToS caveats.
9. Run `bash scripts/ci-local.sh` — all gates pass (the `tests/` root dir is in the pytest allowlist).

### 3. `stripe-parallel-endpoint-fix`

**Trigger condition:** Any fix to Stripe billing behaviour. User says "fix billing X", "stripe webhook Y", or a bug is discovered in the Stripe checkout/subscription flow. Triggered automatically when editing `backend/routers/billing.py` OR `backend/routers/stripe_webhooks.py`.

**Steps it would automate:**

1. Read `backend/routers/billing.py` and `backend/routers/stripe_webhooks.py` side-by-side — they are parallel webhook entry points for the same Stripe event types. Any fix to one almost always applies to both.
2. Identify the shared service abstraction the fix should live in (e.g. `idempotency.py`, `stripe_service.py`, `billing_helpers.py`) — prefer adding the new logic there rather than duplicating across both routers.
3. Apply the fix to both routers in the same commit. Never patch only one.
4. Add/update a regression test in `backend/tests/test_security_hardening.py` (for security/idempotency concerns) or `backend/tests/test_billing.py` (for business-logic concerns):
   - Test must fail on `HEAD~1` (pre-fix) and pass after — document this in the commit message.
5. Verify with `bash scripts/ci-local.sh` — ALL GATES PASSED.
6. Commit message: `Fix: <description> (billing.py + stripe_webhooks.py) (#<issue>)`.

**Evidence:**
- `3a958e5` (2026-06-22): Idempotency row release on webhook handler failure — BOTH `billing.py` and `stripe_webhooks.py` needed the same `idempotency.delete_key()` in their `except` blocks. Bug commit message explicitly notes "A prior subconscious-bot commit (60fcebf1) planned this fix but committed only planning artifacts, no code — the bug was still live."
- `45a228a` (2026-06-16): Disable Stripe Link — BOTH `billing.py` and `stripe_webhooks.py` needed `payment_method_types` restriction.
- Without the parallel-patch discipline, `3a958e5` would have left one endpoint still dropping events, causing intermittent dunning failures that are hard to reproduce.

**Estimated time saved:** 10–15 min per billing fix (remembering to check both files, finding the right test file, writing the HEAD~1 regression check). More importantly, prevents the class of bug where only one endpoint is patched and the other silently keeps the old behaviour.

### 4. `security-endpoint-audit`

**Trigger condition:** A batch of new endpoints lands (feature sprint, onboarding flow, admin tools). User says "security pass on recent endpoints", "audit the new endpoints", or after any sprint that added 3+ new routes. Also triggers after `security-audit` flags items deferred to a future session.

**Steps it would automate:**

1. Identify recently-added endpoints since the last security audit:
   ```bash
   git log --since="<last-audit-date>" --oneline -- backend/routers/ | grep -v "Fix\|test\|chore"
   ```
2. For each new endpoint, run the security checklist:
   - **Tenant isolation**: `_verify_tenant` called on every path that takes `tenant_id` or `client_id`
   - **Webhook sig**: Stripe/Twilio endpoints call the appropriate `construct_event` / `verify_twilio_request`
   - **HTML email escaping**: Any email-generating endpoint uses `html.escape()` on user-controlled content
   - **SSRF**: Any endpoint that fetches a user-supplied URL uses `backend/services/url_validation.py:is_safe_url()` — not a local copy
   - **Rate limiting**: `@limiter.limit(...)` on public-facing or resource-intensive endpoints
   - **Auth**: Route requires the correct role (owner/admin, not just any authenticated user)
3. Produce `audits/audit-security-recent-endpoints-YYYY-MM-DD.md` with:
   - CRITICAL / HIGH / MEDIUM / LOW findings
   - Each finding: endpoint path, file:line, description, recommended fix
   - Items verified as clean: explicit list, don't leave them ambiguous
4. For CRITICAL/HIGH findings, immediately invoke `security-patch-from-review` skill on the audit file.
5. For each new test added by the fix, wire its path into `.github/workflows/pr-check.yml` pytest `--ignore` allowlist if it lives outside `backend/tests/`.

**Evidence:**
- `3d2bd3e` (2026-06-18): Audit `audits/audit-security-recent-endpoints-2026-06-18.md` — explicitly labeled "Item 2 of the security pass", covering `signup_alert`, `lead_alerts`, `front_desk_health`, `os_*`, `instant_kb`, `auto-kb`.
- `645b323` (2026-06-18): Fix — SSRF guard consolidation, hardening `url_validation.py`, adding `tests/test_url_validation.py` (12 tests), wiring into `pr-check.yml`.
- `737f02a` (2026-06-18): Follow-up security fix — redirect re-validation on direct httpx fetchers (the LOW item from the audit).
- The existing `security-audit` skill covers full-codebase scans; this skill is narrower — it's the "new endpoints after a feature sprint" pattern, which was done twice in one day as a sequential audit+fix loop.

**Estimated time saved:** 20–30 min per security pass. The distinct value over the existing `security-audit` skill is: (a) scoped to recently-added endpoints only (not full codebase), (b) produces a dated audit artifact in `audits/`, (c) includes the "wire new tests into pr-check allowlist" step that was done manually in `645b323`.
