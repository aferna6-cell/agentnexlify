## Proposed Skills

### 1. `security-audit`

**Trigger condition:** User says "run a security audit", "check for vulnerabilities", "security review", or before any PR merge involving auth/webhooks/OAuth endpoints.

**Steps it would automate:**
1. Scan all routers for missing tenant verification (`_verify_tenant` calls)
2. Scan for unverified webhook endpoints (Twilio, Stripe, Resend — each has its own signature pattern)
3. Scan for raw `tenant_id` in OAuth `state` parameters (should be JWT-signed)
4. Scan frontend/widget for unescaped user-controlled strings (XSS via innerHTML or `_esc()` gaps)
5. Scan for `from __future__ import annotations` in router files (FastAPI killer)
6. Check CORS config in main.py matches known allowed origins
7. Classify findings by severity (HIGH/MEDIUM/LOW)
8. Write structured fix list with file:line references
9. Apply fixes in severity order, commit with structured message following the `fix(security): patch N <SEVERITY> vulnerabilities — <list>` convention

**Evidence:**
- `c815703` — "patch 8 HIGH-severity vulnerabilities" (Twilio verification, OAuth state signing, XSS, JWT secret). Numbered fix list in commit body.
- `c73a1ff` — "patch MEDIUM vulnerabilities — XSS, SSRF, tenant isolation, HTML escaping". Same structure, same same day.
- `4f0eec9` — "security + operator precedence bugs found by QA" — tenant verification missed on a new endpoint.

Three security fix commits in one week, all following the same scan → classify → numbered-fix → structured-commit pattern. The two main patches were sequential (HIGH first, MEDIUM second), suggesting a deliberate severity-ordering discipline.

**Estimated time saved:** 30–60 min per occurrence. Audit + classification + structured commit currently requires manually reading 53 router files.

### 2. `dead-code-sweep`

**Trigger condition:** User says "clean up dead code", "remove unused files", "refactor — dead code", or after a major feature is deleted/replaced.

**Steps it would automate:**
1. Scan for files that are never imported anywhere (`import X` / `from X import` absent across codebase)
2. Scan for functions/methods that are defined but never called
3. Scan for unused imports within files (pyflakes-style)
4. Scan for dead config keys (settings referenced nowhere)
5. Scan for frontend pages that have no route in App.jsx / Sidebar
6. Cross-check widget/agentnexlify-widget.js vs frontend/public/widget/ for sync (already tracked in CLAUDE.md)
7. For each candidate: verify it's actually dead (not used via dynamic import, not a public API)
8. Delete confirmed-dead items in order: files → functions → imports → config
9. Commit with structured message listing counts: "remove dead code — N dead files, N dead functions, N unused imports, N dead config"

**Evidence:**
- `1e0258e` — "remove dead code — 7 dead files, 5 dead functions, 7 unused imports, dead config". Commit body explicitly lists everything removed and 5 items that were falsely flagged (important: false-positive verification step).

One large sweep this week. The false-positive list in the commit body shows this requires careful judgment, not just grep-delete. A skill would codify the verification step.

**Estimated time saved:** 20–45 min per occurrence. Manual scanning 53 routers + frontend pages is tedious. The false-positive verification (dynamic imports, public APIs) is the hard part the skill would need to encode.

### 3. `tenant-chatbot-audit`

**Trigger condition:** User says "audit [tenant name]'s chatbot", "the bot isn't working for [client]", "something is wrong with [tenant] widget", or receives a client complaint about chatbot quality.

**Steps it would automate:**
1. Pull tenant's widget_config: bot_name, knowledge_base, custom_instructions, booking_enabled, api_key
2. Pull the last N chat_messages for that tenant — look for unanswered questions, fallback responses, error patterns
3. Pull the tenant's FAQ entries — check for contradictions, leakage from other tenants, missing categories
4. Verify conversations RLS policies are in place (silent INSERT failures are a known killer — see migration 080)
5. Check for orphaned sessions (sessions in chat_messages with no row in conversations table)
6. Check widget_config.knowledge_base is populated (empty = bot can't answer domain questions)
7. Identify spam/junk traffic patterns (single-char messages, repeat greetings)
8. Produce audit report: data gaps, RLS issues, FAQ quality, session orphans, code-level bugs
9. Fix in order: DB fixes → migration if needed → code fixes → populate KB/FAQ → verify

**Evidence:**
- `f18faa5` — "MTOptions chatbot audit — RLS root cause, spam filter, knowledge base, lead capture". LLM Council audit revealed 7 bugs: missing RLS policies (120 of 146 sessions silently failing), leaking FAQ entries from other tenants, contradictory FAQ content, 120 orphaned sessions, missing knowledge_base content, code-level spam/junk handling missing.

One very thorough audit this week. The pattern is repeatable for any tenant showing symptoms (low lead capture, bad bot responses). The RLS root cause (no policies despite RLS enabled since migration 001) is specifically worth encoding since it's silent and catastrophic.

**Estimated time saved:** 45–90 min per occurrence. Audit currently requires manually querying Supabase, reading logs, and knowing to check RLS policies specifically.

### 4. `security-patch-from-review`

**Trigger condition:** After a PR code review produces a structured list of findings (C1, C2, H1, H2, M1...), or after a Codex/agent branch audit returns findings.

**Steps it would automate:**
1. Parse the review findings list (Critical → High → Medium → Low ordering)
2. For each finding: identify the exact file and function, apply the minimal targeted fix
3. Track which findings are addressed vs skipped (with reason)
4. Verify no regressions: run related tests
5. Commit with structured body matching the review's classification (C1: ..., H1: ..., etc.)

**Evidence:**
- `a7cc5bb` — "resolve all review findings from codex branch audit". 13 findings (C1–C2, H1–H4, M1–M4, L1–L3), all addressed and documented in commit body with the same codes used in the review.

This is distinct from `security-audit` (which generates the finding list) — this skill consumes an existing finding list and systematically closes every item. The key discipline: same classification codes in the commit as in the review, so it's auditable.

**Estimated time saved:** 15–30 min per occurrence. Currently requires careful reading of the review, keeping mental state of what's done, and writing the commit body from scratch.
