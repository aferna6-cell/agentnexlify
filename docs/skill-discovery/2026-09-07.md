### 1. `meter-ai-endpoint` — Reserve/Record/Release Metering Wrapper

**Trigger condition:** Any task adding or retrofitting metering to a backend function that calls `call_claude_messages` or `anthropic.Anthropic().messages.create()`.

Phrases that should trigger this:
- "meter `<function>`"
- "add usage guard to `<service>`"
- "reserve/record/release for `<endpoint>`"
- "unmetered AI path"
- `check_ai_metering.py` reports a violation

**Steps it would automate:**

1. **Identify the unmetered function** — locate the call site flagged by `scripts/check_ai_metering.py path:function:line`.
2. **Add imports** — `reserve_ai_tokens`, `record_ai_usage`, `release_ai_token_reservation`, `estimate_widget_chat_tokens` from `backend/services/ai_usage_guard`.
3. **Write `_load_<service>_budget_tenant(db, tenant_id)`** — selects `id, plan, ai_monthly_token_alert_threshold, ai_monthly_token_hard_limit` from `tenants`, returns `None` on missing row or exception, logs a warning with `tenant=` but no PII.
4. **Wrap the Claude call with the three-phase lifecycle:**
   - Load tenant → fail closed if `None` before provider
   - `reservation = reserve_ai_tokens(db, tenant, estimated_tokens)` — return early if denied
   - Call Claude
   - `record_ai_usage(db, reservation, actual_tokens)` on success
   - `release_ai_token_reservation(db, reservation)` in the exception handler
5. **Write `backend/tests/test_<service>_usage_guard.py`** — 4 required test cases every time:
   - Budget denial → function returns/skips without calling Claude
   - Success → reservation recorded, Claude was called exactly once
   - Failed record → reservation released, no uncaught exception
   - Missing tenant → fails closed before provider (no Claude call)
6. **Add new test file to `.github/workflows/pr-check.yml`** pytest command (append to the long `-q` line in "Run backend tests with coverage" step).

### 2. `staging-preflight` — Feature-Specific Dry-Run Smoke Script

**Trigger condition:** A new feature or migration needs a staged check-only verification pass against the staging environment before it can be declared production-ready.

Phrases that should trigger this:
- "staging preflight for `<migration>`"
- "dry-run check for `<feature>` against staging"
- "smoke test before we apply migration-NNN"
- "check-only staging readiness"

**Steps it would automate:**

1. **Create `scripts/<feature>_staging_<preflight|smoke>.py`** with:
   - `--dry-run` flag (default: `True`; must opt-in to mutating mode)
   - `--env` flag for `staging` / `prod` (default: `staging`)
   - A `RunResult` dataclass with `passed: bool`, `checks: list[str]`, `errors: list[str]`
   - Each check as a named function returning `(bool, str)` — name becomes the check label
   - A `main()` that runs all checks, prints a summary table, exits 0/1
2. **Create `tests/test_<feature>_staging_readiness.py`** — unit tests for the script contract:
   - Dry-run mode does not mutate (mock Supabase, assert no write calls)
   - Expected checks are present in the result
   - Error path produces `passed=False`
3. **Do NOT add staging preflight tests to `.github/workflows/pr-check.yml`** — they require live credentials; they're manual / Routine-invoked only.

**Evidence:**

2 occurrences in one week. Prior weeks had similar patterns (`check_schema_log_migrations.py`, `check_ai_metering.py`). The naming and structure diverges slightly each time — a skill would standardize it.

**Estimated time saved:** 20–30 min per preflight. Mainly from not re-inventing the `--dry-run`/`--env` flag pattern, `RunResult` shape, and CI exclusion decision each time.
