## Proposed Skills

### 1. `service-auth-hardening`

**Trigger condition:** A new internal microservice (Node.js, Python, or otherwise) is about to be activated in production by setting a `SERVICE_URL` env var. The service currently has no auth between itself and its calling service. User says "harden service auth", "add auth to service before activating", "secure the boundary between X and Y before going live", or a `SERVICE_URL` is about to be added to Railway.

**Steps it would automate:**

1. Identify the compute endpoints (e.g. `/orchestrate`, `/agents/:name/run`) vs the open endpoint (`/health` for Railway healthcheck) — never block the healthcheck.
2. Create `src/auth.ts` (or equivalent) as a pure function: `(req) => boolean` — no I/O, unit-testable in isolation.
3. Wire the auth check into the server: 401 with JSON body if token missing/wrong, pass-through if token matches. Token unset = open mode (local dev parity — do NOT enforce when env var is absent).
4. Add the `X-<Service>-Token` header to both POST calls in the calling service client (FastAPI `agent_sdk_client.py` pattern: send header only when token is configured, no-op otherwise).
5. Write unit tests for the pure auth module (3 cases: valid token, invalid token, no token when unset = open mode).
6. Write integration tests in the calling service (2 cases: token configured → header present, token absent → no header).
7. Write `DEPLOY.md` in the service root with: security model (what the service holds / can affect), one-time deploy steps (root dir, Dockerfile path, env vars + their effects), activation steps (what env var to set on calling service + restart needed), 3-bullet verify section (basic function, correctness, auth roundtrip), rollback section (which env var to unset + what persists safely).
8. Commit as a single PR with title "Harden <service> auth before v2 activation" — include DEPLOY.md in the same commit.

**Evidence:**
- `abccdc3` (2026-06-06, PR #205): "Harden agent-service auth before v2 engine activation" — extracted `agent-service/src/auth.ts` (16 lines, pure), wired 401 at `/orchestrate` + `/agents/:name/run`, kept `/health` open, added `X-Agent-Token` header injection in `backend/services/agent_sdk_client.py`, wrote `auth.test.ts` (25 lines, 3 cases), `test_agent_sdk_client.py` (73 lines), `agent-service/DEPLOY.md` (60 lines). Exact 7-step pattern above executed in one PR.
- This PR was explicitly sequenced before `abccdc3`'s twin `617b667` (PR #207): "Activating the v2 Agent OS engine means setting AGENT_SERVICE_URL in production, so harden the boundary first."
- The DEPLOY.md structure is reusable: security model + deploy + activate + verify + rollback.

**Estimated time saved:** 35–50 min per service boundary. The non-obvious parts are: (a) the token-unset = open-mode dev parity requirement (not enforcing when env var is absent), (b) keeping `/health` always open for the platform healthcheck, (c) the DEPLOY.md structure with rollback instructions. Without this skill, these are likely to be forgotten, requiring a follow-up PR.

### 2. `phase-report-closeout`

**Trigger condition:** A major feature was merged last week or earlier this week and produced a verification report with numbered items (F-01, F-02, ..., or numbered audit findings). Some items were closed in the initial PR; others remain open. User says "close the remaining phase N items", "verification report has open items", "F-0N findings", or after a big feature lands and the next step is polishing report findings.

**Steps it would automate:**

1. Read the verification/audit report — identify all open numbered items (e.g. F-03/F-04/F-05/F-06).
2. Group items by theme: display items together, data pipeline items together, correctness items together. Never mix unrelated items in one commit.
3. For each group:
   a. Implement the code change (TypeScript agent, Python router, JSX component).
   b. Write or extend the test file for that change — confirm test count in note.
   c. If a migration is needed, create it as `migrations/NNN_description.sql` and apply via Supabase MCP **separately** from the code commit, then note "Migration NNN applied separately via Supabase MCP" in the commit message.
   d. Do NOT combine migration application with code commit (schema must be live before code ships).
4. Confirm all test suites in the commit message: "frontend 38/38 (added X case), agent-service 11/11 (added Y suite), tsc clean, frontend build clean."
5. Reference original report item numbers in commit body (e.g. "Closes F-03 + F-06 (routing transparency)").

**Evidence:**
- `617b667` (2026-06-07, PR #207): Closed Phase 3 display items — fixed v2 response shape rendering in `AgentRunFlowchart.jsx` (dual-shape tolerance), fixed `Review draft` button gating. These were discovered during a verification pass that found "the backend v2 engine working in production but the dashboard rendering against the v1 response shape."
- `d20284f` (2026-06-07, PR #208): Closed remaining Phase 3 items F-03/F-04/F-05/F-06 — routing chip in `AgentRunFlowchart`, legacy-draft rejection in migration 132, slot extraction in `extract-slot.ts`. Migration applied separately. Test counts confirmed: "frontend 38/38, agent-service 11/11."
- Both commits reference F-0N item numbers. Both were preceded by reading verification output (the "Phase 3 verification found..." text in commit messages). Both followed the grouped-by-theme pattern.

**Estimated time saved:** 20–30 min per report. The overhead is: (a) reading the report and organizing which items group together, (b) remembering to apply migrations separately, (c) knowing to confirm test counts from all layers in the commit message. The skill codifies the sequencing rule (migration before code) and the commit message format.
