### 1. `god-class-splitter`

**Trigger condition:** User says "split X", "factor out X", "X is too big", "refactor god class in X", or when `improve-architecture` output flags a file >600 lines as having multiple concerns.

**Steps it would automate:**
1. Read `plans/god-class-refactor_plan.md` to check if the target file is already queued with a suggested split axis
2. `wc -l <target>` — confirm it exceeds the 600-line threshold (Rule 9)
3. Read the full file — identify 2–3 independent concerns (name each concern)
4. Propose module names for extracted files (`<concern>_service.py`, `<concern>_fetch.py`, etc.) — wait for approval if ambiguous
5. Extract each concern to a new module, moving only the symbols that belong to it
6. Grep ALL importers of the old module and update every call site in the same pass (`grep -rn "from backend.services.old_module\|import old_module"`)
7. Delete or thin the original file — no re-export shims left behind
8. Register any new routers in `backend/main.py` if the split produced new router files
9. Run `python3 -m pytest <test_file> -x --tb=short -q` — confirm pass count unchanged
10. Verify: `grep -rn "backend.services.old_module" .` returns nothing (no stale importers)
11. Write a brief `tests/test_extracted_<module>.py` smoke test file covering the new module's public surface (endpoints + pure functions)
12. Commit as one atomic PR — no half-splits across commits

**Evidence:**

- `d8a89f3` (2026-05-22): Follow-up auto-commit to complete the local_seo_fetch extraction
- `2174732` (2026-05-23, PR #180): Split 5 files simultaneously — `branding_service.py`, `control_center.py`, `channels_facebook.py`, `pipeline.py`, `social_media.py` — created 12 new service modules + 897-line `test_extracted_services.py`

- PR #180 commit message says "splits 5 god-class routers/services into focused modules; adds 60+ tests for extracted services" — confirming the write-tests step is always part of the workflow
- 29 backend files and 25 frontend files still exceed 600 lines per `plans/god-class-refactor_plan.md` — this skill will recur weekly until the backlog is cleared

**Estimated time saved:** 20–40 min per file split. The pattern is now codified in `plans/god-class-refactor_plan.md` but currently requires reading that doc + the god-class rules + the target file before starting. A skill removes the context-loading overhead and enforces the 12-step checklist, which was violated in both splits this week (local_seo split required a follow-up auto-commit; PR #180 required `5f2cd2b` to repair test imports afterward).

### 2. `post-split-test-repair`

**Trigger condition:** Immediately after any god-class split or module rename, when `pytest` shows `ModuleNotFoundError` or `MagicMock` patch targets resolve to `AttributeError`. Also triggered when user says "tests broke after split", "stale patch targets", "repoint imports after refactor".

**Steps it would automate:**
1. Run `python3 -m pytest tests/ -x --tb=short -q 2>&1 | head -40` — capture first failure
2. Identify the old module path referenced in the failure (e.g. `backend.routers.local_seo._generate_keywords`)
3. Grep all test files for the old path: `grep -rn "backend.services.old_module\|backend.routers.old_router" tests/`
4. For each stale reference, determine the new canonical path by checking what was extracted where
5. Update `@patch("old.path")` decorators to point to the new module
6. Update `from old.module import X` statements to the new location
7. Re-run pytest — repeat until green
8. Commit as `test: repoint stale patch targets and imports after <split-name> refactor`

**Evidence:**
- `5f2cd2b` (2026-05-22): "test: repoint stale patch targets and imports after refactor" — repaired 21 stale patch targets across `test_auth_endpoints.py`, `test_local_seo.py`, `test_onboarding_ai_paths.py`, `test_retry_policy.py`. Commit message body says "Repair 21 pre-existing root-suite failures caused by test drift after the local_seo god-class split."
- `4afb3cf` (2026-05-22): "Fix test_local_seo_parsers import: parsers live in local_seo_scoring" — one-line fix for a single stale import, same class of problem
- Both commits happened within hours of the local_seo split (`3555645`) — confirming this is a predictable follow-up
- After PR #180 (5-file split), the same class of repair would be required for any tests importing from the old module paths

**Estimated time saved:** 15–20 min per split. Currently this is a separate commit requiring: run pytest, read output, identify old paths, grep tests, manually update each, re-run. A skill encodes the search-and-replace workflow so it runs in one pass. The pattern is identical each time (old path → new path in `@patch` strings and imports).

**Note:** This skill is tightly coupled to `god-class-splitter` — consider whether it should be a sub-step of `god-class-splitter` (step 11.5) rather than a standalone skill. Standalone is better if the repair needs to run days after the split when test drift compounds.

### 3. `billing-constant-guard`

**Trigger condition:** User says "fix plan pricing", "billing mapping wrong", "AMOUNT_TO_PLAN", "plan prices changed", or when a billing-related bug is fixed and no contract test exists for the affected constant/dict.

**Steps it would automate:**
1. Read `backend/routers/billing.py` — locate `AMOUNT_TO_PLAN` and `PLAN_TO_STRIPE_PRICE` constants
2. Cross-reference values against `CLAUDE.md` plan price table (growth=$99, autopilot=$150, professional=$250, enterprise=$899)
3. Identify missing or wrong entries — compare current dict keys against expected `price_cents` values
4. Fix the dict — add missing current-price entries, preserve legacy entries with comments
5. Find any existing test file that asserts the old (now-wrong) constant values: `grep -rn "AMOUNT_TO_PLAN\|15000\|25000\|99\|150\|250\|899" backend/tests/`
6. Check if any tests are **inverted** — asserting `X NOT IN` when `X` should now be present, or asserting old prices as "current"
7. Update inverted/stale test assertions to match the corrected constant — do NOT change tests without understanding why they were written (check commit that introduced them)
8. Add parametric contract tests if none exist: one method per plan tier × one for `AMOUNT_TO_PLAN` × one for `PLAN_TO_STRIPE_PRICE`
9. Verify CI wiring: check `.github/workflows/pr-check.yml` — confirm the test file is included in the test run
10. Commit: `fix: correct AMOUNT_TO_PLAN for <plan> ($NNN/mo), update contract tests`

**Evidence:**
- `c72b535` (2026-05-22): "Fix AMOUNT_TO_PLAN: correct $150/$250 plan mappings, add enterprise" — first fix attempt, corrected wrong entries but still missing 15000 and 25000
- `1eaaeec` (2026-05-22): "Fix billing AMOUNT_TO_PLAN" — second attempt, same bug, still did not add the missing entries
- `1553bf7` (2026-05-23) + subconscious runs 30–32: Three consecutive subconscious runs all identified that:
  - The fix was still incomplete (15000→autopilot and 25000→professional missing)
  - `test_billing_amount_to_plan.py` had inverted assertions (`15000 NOT IN AMOUNT_TO_PLAN`) that blocked CI from going green after a correct fix
  - The test file was wired into CI (`pr-check.yml`) after the inverted assertions were already there
- Two commits and three AI runs to fix one dict — total ~90 minutes of repeated work on the same bug class
- Plan prices in `CLAUDE.md` are the source of truth; tests were written against a stale understanding of "correct" prices

**Estimated time saved:** 30–45 min per occurrence. The triple-fix pattern this week shows the workflow lacks a checklist — specifically, the "check for inverted tests" step is non-obvious and was skipped twice. The CLAUDE.md plan table is the authoritative source but isn't checked during billing fixes.
