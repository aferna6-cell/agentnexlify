## Proposed Skills

### 1. `moratorium-sprint`

**Trigger condition:** User says "moratorium sprint", "clear pending items", "exit moratorium", "execute the sprint", or when `subconscious/state/governance.json` shows `moratorium_active: true` and user asks Claude to implement the backlog.

**Steps it would automate:**
1. Read `subconscious/state/governance.json` — extract all `active_directions` where `status` is `pending_approval`
2. Filter to S-effort items (≤30 min each) — skip M/L-effort items that require deliberate sprint allocation
3. For each S-effort item: locate the `winning-concept.md` from its run number (e.g. `subconscious/runs/2026-05-15-pm/winning-concept.md` for run 22)
4. Read the "Implementation Sketch" section — each has step-by-step instructions with exact file paths and code blocks
5. Create a single branch `moratorium-exit-sprint` (or timestamp variant)
6. Execute items sequentially in order of shortest-first (reduce risk, build momentum)
7. After each item: commit with the prescribed message from the sketch, run `python3 scripts/check_project_invariants.py` to verify
8. After all items: open a draft PR against main with a summary table (item, effort, sketch ref, commit SHA)
9. Update `governance.json` — set `pending_approvals` count and `moratorium_active: false` if threshold met

**Evidence:**
- Subconscious runs 15–23 (9 consecutive runs, 10 days) all reached the same conclusion: S-effort items are ready to implement but no skill/command exists to execute them from context
- Run 23 (2026-05-18) winning concept explicitly proposed a `/sprint` slash command with this exact sequence
- Run 23 candidate ideas §Idea 3 specifically proposed `.claude/commands/sprint.md` that reads `governance.json` → filters S-effort → executes sketches
- Implementation sketches exist for all 4 current pending S-effort items with exact file edits and commit messages pre-written
- Without this skill, each session re-reads all the context (governance.json, 4+ winning-concept.md files, improvement-backlog.md) before doing work — ~15 min of context loading per attempt

**Estimated time saved:** 15–20 min of context loading + 50 min of implementation = effectively converts a 65-min manual multi-session affair into a single `/moratorium-sprint` invocation. Recurs every time moratorium re-triggers (already happened twice: runs 1-13, runs 15+).

### 2. `pre-commit-guard-add`

**Trigger condition:** User says "add a pre-commit check", "block X in pre-commit", "add Check N to hooks", or when a bug pattern is identified that could be caught at commit time.

**Steps it would automate:**
1. Read `scripts/hooks/pre-commit` to determine the current highest Check N number and understand the hook's structure
2. Read existing checks to ensure the new check doesn't duplicate an existing one
3. Determine the correct insertion point (checks are ordered by specificity; language-specific checks group together)
4. Write the new check block following the existing pattern: `echo -n "Check N: <description>... "` → run detection → `exit 1` on match → `echo -e "${GREEN}OK${NC}"`
5. Add an opt-out escape hatch comment pattern (e.g. `// ok-silent-catch`) if the pattern has legitimate exceptions
6. Test: stage a file that triggers the pattern, run `scripts/hooks/pre-commit`, confirm it exits 1
7. Test: stage a clean file, confirm the hook exits 0
8. Update `CLAUDE.md` if it references the pre-commit hook (the hook section under "Automation")
9. Commit the hook change as its own atomic commit: `chore: add Check N — <description>`

**Evidence:**
- `72f8204` (2026-05-05): "fix(admin-analytics): add console.warn to 6 silent catches, add pre-commit Check 9" — added `.catch(() => null)` silent-catch detection with `// ok-silent-catch` opt-out
- Check 10 (`check_project_invariants.py`) has been pending for 23 days across 7 improvement backlog entries (runs 8, 15, 16, 17, 18, 22, 23) — the pattern is clear and the implementation sketch is pre-written but re-derived each session
- Pattern: every new class of bug → new numbered check. The numbering and structure are consistent but currently require reading the whole hook file each time to find the right insertion point and format.

**Estimated time saved:** 15–20 min per new guard (currently: read hook, understand format, find insertion point, write check, test, update CLAUDE.md). Recurs every time a new bug class is identified — historically 1-2 per month.

### 3. `dep-batch-merge`

**Trigger condition:** User says "merge safe deps", "clear dependency PRs", "merge the Dependabot PRs", or as part of morning routine when `morning-digest` lists open dependency PRs.

**Steps it would automate:**
1. List all open PRs via `mcp__github__list_pull_requests` — filter to dependency bump PRs (title contains "bump", "update", author is Dependabot)
2. Classify each by risk tier:
   - **Safe (merge immediately):** patch version bumps, minor version bumps for dev-only deps (eslint, playwright, test runners)
   - **Test required:** minor version bumps for runtime deps (uvicorn, FastAPI, pydantic)
   - **Review required:** major version bumps (cross-env 7→10, eslint 9→10)
3. For Safe PRs: merge each via `mcp__github__merge_pull_request` with merge commit
4. For Test-required PRs: note them with a specific test command (`npm run build` for frontend, `python -m pytest` for backend)
5. For Review-required PRs: add a comment explaining the major bump concern and flag for human decision
6. Report: table of PRs merged, PRs needing tests, PRs flagged for review

**Evidence:**
- Morning digest 2026-05-18 identified 4 immediately-safe PRs: #163 (`@typescript-eslint/parser` patch), #164 (`@playwright/test` minor), #102 (`youtube-transcript-api` patch), #103 (`python-multipart` patch) — all flagged "Safe — merge"
- Morning digest 2026-05-15 had a similar set of accumulating dependency PRs
- 10 open dependency PRs total (morning digest count), aging 7–28 days — safe ones sit idle because there's no fast path to merge them
- The classification logic (patch = safe, major = review, dev-dep minor = safe) is consistent but currently applied manually each time by re-reading PR titles

**Estimated time saved:** 10–15 min per batch (currently: open each PR, assess, merge individually). Recurs weekly as Dependabot files new PRs. Higher value is preventing safe PRs from aging 28+ days and creating merge conflicts.

### 4. `governance-state-sync`

**Trigger condition:** User says "sync governance state", "fix governance.json", "governance is stale", or invoked automatically at the start of a subconscious run when evidence contradicts governance.json state.

**Steps it would automate:**
1. Read `subconscious/state/governance.json` — extract `active_directions`, `moratorium_config`, `pending_approvals`
2. For each `active_direction` with status `pending_approval`: verify whether the implementation actually exists in the codebase (grep for the prescribed file/script/hook addition)
3. For each `active_direction` with status `implemented_unverified`: check git log for the commit that implemented it, verify the file exists, promote to `implemented_production_verified` if it has been in production >7 days
4. Recount `pending_approvals` from the verified list and update the field
5. Check `moratorium_active` against the recount: if `pending > threshold`, set `true`; if `pending ≤ threshold`, set `false`
6. Write corrections back to `governance.json` with a git commit: `chore: sync governance.json state — N corrections`
7. Report: list of corrections made (what was wrong → what it is now)

**Evidence:**
- Run 14 memory: "moratorium_active corrected to true, pending_approvals corrected to 4" — governance had drifted after run 13 implementation
- Run 16: "widget_helpers split: `implemented_unverified` → `implemented_production_verified` (23 days production, zero errors)"
- Run 15 memory explicitly labeled `mode: moratorium_retriggered` — governance.json had `moratorium_active: false` even though `pending_approvals=4 > threshold=3`
- Corrections appear in 4 of the 7 runs this week — this is routine friction, not exceptional behavior
- Each correction currently requires reading governance.json, reading git log, grepping codebase, then writing back — ~10 min of work done informally at the start of every subconscious run

**Estimated time saved:** 8–12 min per subconscious run (removing the ad-hoc correction step). Compounds: if subconscious runs 2x/day, saves 30–45 min/week.
