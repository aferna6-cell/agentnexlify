## Proposed Skills

### 1. `feature-flag-module`

**Trigger condition:**  
A new AI feature or external-action capability is being added behind a feature gate (default-off for production safety).

**What it would automate:**  
This week M7 added `rag_flags.py` and M8 added `m8_action_flags.py`. Both are byte-for-byte identical in structure to the existing `SEND_EMAIL_ENABLED` pattern. Every new capability follows the same six-step sequence manually:

1. Create `backend/services/<feature>_flags.py` from the standard template:
   - Module docstring: "X flag. Defaults fail-closed. Must stay OFF until evals + smoke pass."
   - `_TRUTHY = frozenset({"1", "true", "yes", "on"})`
   - `_flag(name)` env-reader helper
   - One `<feature>_enabled() -> bool` per flag
2. Create matching `agent-service/src/agent-os/actions/flags.ts` entry (or add to existing `flags.ts`)
3. Create `backend/tests/test_<feature>_flags.py` with: off-by-default, truthy values, false values
4. Update `docs/ops/m<N>-staging-setup.md` staging variables table with the new flag
5. Add the flag to the nightly-commit-review `__future__` + flag scan (pre-commit catches it)
6. Record the flag name in `docs/dev-knowledge/schema-log.md` if it gates a migration

**Evidence:**
- `18652f3` — `feat(m7): tenant RAG — eval first, BM25 retrieval, default-off flag` → creates `backend/services/rag_flags.py` + `agent-service/src/agent-os/rag/flags.ts`
- `41aecb5` — `Milestone 8: Calendar + CRM Business Actions (tools, safety, eval — flags OFF)` → creates `backend/services/m8_action_flags.py` + adds to `agent-service/src/agent-os/actions/flags.ts`
- `2de21d2` — `feat(agent-os): Sales-only send_email behind default-off flag` (prior week, same pattern)
- `c159976` — `fix(nightly): remove __future__ annotations from m8_action_flags service` → auto-nightly caught a flag file that violated the no-`__future__` rule, confirming the flags file is always touched in the same PR as the feature and sometimes needs a follow-up fix

All three modules are structurally identical. `platform_flags.py` is the DB-backed cousin for stable flags (migration 175); new gating flags go in the per-feature module pattern, not `platform_flags.py`.

**Files touched every time:**
- `backend/services/<feature>_flags.py` (new)
- `backend/tests/test_<feature>_flags.py` (new)
- `agent-service/src/agent-os/actions/flags.ts` (extend) or `agent-service/src/agent-os/<feature>/flags.ts` (new)
- `docs/ops/m<N>-staging-setup.md` (extend variable table)

**Estimated time saved:** 15–20 min per new capability (template generation, test boilerplate, cross-file sync). ~3 new flags per month at current pace.

### 2. `milestone-staging-smoke`

**Trigger condition:**  
A milestone's offline eval passes and it's time to prove the feature on staging before setting production flags.

**What it would automate:**  
This week saw 5 separate staging smoke runs across commits `62ea09c → fa83852`. Each run followed the same sequence, building on `scripts/m8_live_smoke.py`:

1. **Gate check:** confirm `M8_SMOKE_AUTHORIZED=1`, `M8_SMOKE_ENV=staging`, `M8_SMOKE_CLIENT_ID=<smoke-tenant>` set; refuse to run otherwise (never silently target production)
2. **Suite selection:** declare which suites to run (`rag`, `calendar`, `crm`, `gmail`, `isolation`, `agent_os_e2e`); skip suites whose dependencies are unmet (OAuth not connected = honest stop, not silent pass)
3. **Evidence capture:** write timestamped JSON artifact to `audits/artifacts/m<N>-live-smoke-<TIMESTAMP>Z.json` with: git SHA, env name, per-suite results (pass/skip/fail + reason)
4. **Next-actions update:** update `audits/artifacts/m<N>-next-actions-<date>.md` with: overall verdict (PASS / HOLD), per-blocker owner-action checklist, confidence score (≥90% = COMPLETE)
5. **Staging runbook update:** amend `docs/ops/m<N>-staging-setup.md` to mark completed steps and surface remaining blockers
6. **Commit with `[skip ci]`** — smoke artifacts are evidence, not code; no CI runner needed

**Files touched every time:**
- `scripts/m<N>_live_smoke.py` (extend suites or add new smoke runner)
- `audits/artifacts/m<N>-live-smoke-<TIMESTAMP>Z.json` (new, timestamped)
- `audits/artifacts/m<N>-next-actions-<date>.md` (new or update)
- `docs/ops/m<N>-staging-setup.md` (update blockers/steps)

**Evidence:**
- `62ea09c` — first smoke runner created
- `2db4802` — extended with RAG + CRM + isolation suites; deploy-proof report
- `b786aeb` — RAG+CRM pass; Calendar/Gmail HOLD; live-proof JSON artifact
- `47cda00` — next-actions update after RLS re-enable
- `fa83852` — step-3 gate: verify staging + wire service key scripts
- Pattern: each blocker resolved → re-run smoke → update artifacts and next-actions

**Estimated time saved:** 20–30 min per milestone (standardized env guard, suite orchestration, artifact naming, next-actions template). Prevents accidental production targeting (a real risk the current `M8_SMOKE_AUTHORIZED` guard was built to address).

### 3. `eval-first-feature`

**Trigger condition:**  
A new multi-turn AI agent capability (tool, action, or retrieval module) is being designed and needs a benchmark before implementation starts.

**What it would automate:**  
This week saw M6, M7, and M8 all follow the same eval-first sequence. Currently these are assembled manually per-milestone:

1. **Design the evaluation schema** — `agent-service/evals/datasets/<feature>/README.md` listing coverage areas (happy path, cross-tenant fail-closed, prompt-injection cannot skip approval, idempotent behavior, flag off = deny)
2. **Write the dataset builder** — `agent-service/evals/datasets/<feature>/build_<feature>_eval_v1.py` that generates synthetic cases with inputs and expected behavior labels
3. **Freeze the eval JSON** — `agent-service/evals/datasets/<feature>/<feature>-eval-v1.json` (deterministic; no model calls)
4. **Write the eval runner** — `agent-service/evals/run-<feature>-eval.ts` with: fixture-path resolution, case-by-case assertions, summary output
5. **Add gate command to `package.json`** — `"eval:<feature>:gate"` script that asserts `unsafe=0` AND `accuracy≥0.95`
6. **Record baseline** — run gate, capture results in `ml/<feature>/artifacts/<feature>-eval-v1-<id>.json`
7. **Only then implement** — implementation PR references "offline eval: X/Y, unsafe=0" in its description

**Evidence:**
- `042381c` — M6 decision intelligence: eval harness, semantics, router bakeoff complete before finalization PR
- `18652f3` — M7: `rag-eval-v1.json` (183 cases), `rag-eval-validation-v1.json`, `run_rag_eval.ts`, gate before BM25 was shipped
- `741f10c` — M7: independent holdout eval to prevent training-set leakage (`rag-eval-holdout-v1.json`, `check_rag_holdout_leakage.py`)
- `41aecb5` — M8: `calendar-crm-eval-v1.json` (265 cases), `run-calendar-crm-eval.ts`, gate `unsafe=0 AND accuracy≥0.95` — eval shipped before the Calendar data-plane was implemented
- `a36f97a` — M8 implementation references the offline eval gate numbers in commit description

**Files touched every time:**
- `agent-service/evals/datasets/<feature>/README.md` (new)
- `agent-service/evals/datasets/<feature>/build_<feature>_eval_v1.py` (new)
- `agent-service/evals/datasets/<feature>/<feature>-eval-v1.json` (generated)
- `agent-service/evals/run-<feature>-eval.ts` (new)
- `agent-service/package.json` (add gate script)
- `ml/<feature>/artifacts/<feature>-eval-v1-<id>.json` (baseline)

**Estimated time saved:** 30–45 min per new feature (dataset builder template, runner boilerplate, gate script wiring, coverage checklist). Prevents shipping capabilities without safety gates (the unsafe=0 gate has caught real issues — M7 commit history shows multiple fix iterations before gate passed).
