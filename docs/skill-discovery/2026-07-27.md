## Proposed Skills

### 1. `feature-docs-trio`

**Trigger:** A backend + frontend feature has shipped (PR merged) but no wiki article, ADR, or runbook exists for it yet. Trigger when commit messages contain `docs(<feature>): KB article` or `docs(<feature>): ADR`, or when a feature PR closes and the commit log shows no corresponding `docs/` commit.

**Pattern observed:** Done **3 times** in 7 days, each time touching the same 4–6 file types:

| Commit | Feature | Files touched |
|---|---|---|
| `717c7f3` (#45) | photo-quote | `knowledge-base/wiki/widget/photo-quote.md`, `docs/dev-knowledge/architecture-decisions.md` (+ADR entry), `knowledge-base/INDEX.md` |
| `14ebe8e` (#54) | drive-kb integration | `knowledge-base/wiki/integrations/drive-kb-onboarding.md`, `docs/dev-knowledge/architecture-decisions.md` (+ADR), `knowledge-base/INDEX.md`, `docs/runbooks/drive-kb-failures.md` |
| `d50d1e8` (#62) | zapier integration | `knowledge-base/wiki/integrations/zapier.md` + 3 CRM-specific guides, `knowledge-base/INDEX.md` (+4 entries), `docs/runbooks/zapier-failures.md` |

All three follow the same structure within 2 days of the last feature PR merging. The pattern is consistent: KB wiki article (Karpathy-style — what, how, tier-gates, failure modes) + ADR entry in `docs/dev-knowledge/architecture-decisions.md` + `knowledge-base/INDEX.md` update + optional `docs/runbooks/<feature>-failures.md`.

**Steps the skill would automate:**

1. Identify the feature: read the closing PR description to extract the feature name, key decisions, and tier gates.
2. Write `knowledge-base/wiki/<category>/<feature-name>.md`:
   - Frontmatter: `title`, `category`, `tags`, `last_updated`
   - Required sections: What it does, How it works (flow diagram in prose), Tier gate (which plan unlocks it), Failure modes, Related articles (wikilinks)
   - Run `npm run kb:lint` — must be clean before committing
3. Add ADR entry to `docs/dev-knowledge/architecture-decisions.md`:
   - Format: `ADR-YYYY-MM-DD-NNN — <title>` + 2-3 sentence rationale + alternatives rejected
4. Add entry/entries to `knowledge-base/INDEX.md` under the correct category section.
5. If the feature has a failure mode the on-call needs to act on: write `docs/runbooks/<feature>-failures.md` with: symptom → root cause → fix steps for each failure class.
6. Commit as `docs(<feature>): KB article + ADR + runbook [skip ci]` — this never needs CI.

**Evidence:** `717c7f3`, `14ebe8e`, `d50d1e8` (commits in 7-day window)  
**Estimated time saved:** 30–45 min per feature shipped (eliminating the "which sections do I need?" overhead, preventing kb:lint violations, catching missing INDEX entries)

### 2. `widget-ai-marker-add`

**Trigger:** Adding a new way for the LLM to trigger a UI action (open a panel, start a flow, transfer to a human) during a widget chat session. Trigger when a task says "the AI should be able to open X" or "add a signal for the model to trigger Y" or "let the AI initiate Z."

**Pattern observed:** Done **2 times** with an identical structure (HANDOFF_REQUESTED, then SHOW_BOOKING_PANEL this week):

| Item | HANDOFF_REQUESTED | SHOW_BOOKING_PANEL (`e9b4972`, #573) |
|---|---|---|
| Prompt instruction | Added to `booking_prompt.py` | Added to `booking_prompt.py` |
| Backend detection | Inline in `widget_chat.py` | Extracted to `widget_chat_booking_action.py` |
| Return signal | `{"handoff": true}` | `{"show_booking": true}` |
| Widget JS response | `if (data.handoff) showHumanHandoff()` | `if (data.show_booking) showBooking('date')` |
| Tenant gate | None | `bookingEnabled` flag check |
| Widget sync | All 3 mirrors byte-identical | All 3 mirrors byte-identical |
| Tests | `test_widget_chat.py` | `test_widget_show_booking.py` (85 lines) |

The second occurrence (SHOW_BOOKING_PANEL) also introduced best-practice improvements over the first: the detection logic was extracted to its own file (`widget_chat_booking_action.py`) rather than being inline, and a tenant gate was added.

**Steps the skill would automate:**

1. Add the marker string to the system prompt in `backend/services/booking_prompt.py` (or the tenant-specific prompt builder): define WHEN the model should emit the marker (ready signal — not generic, specific intent).
2. Create `backend/routers/widget_chat_<action>.py` with a `detect_<marker>` function: strip the marker from `assistant_text`, check the relevant tenant flag (e.g., `bookingEnabled`), return a bool.
3. Wire into `backend/routers/widget_chat.py` step 9-series: import + call `detect_<marker>`, suppress if tenant flag is off, add the signal key to the response JSON, strip the marker so it never appears in rendered text.
4. In `backend/models/schemas.py` (if a Pydantic response model is used): add the optional bool field with `= None` default.
5. In the widget JS (`widget/agentnexlify-widget.js`): add an `if (data.<signal>) { <action>() }` check in the response handler.
6. **Byte-identical sync:** copy the widget JS to `frontend/public/widget/` AND `landing-page-v2/widget/`. Run `scripts/check_project_invariants.py` to confirm.
7. Write `backend/tests/test_widget_<action>.py`: marker in text → signal true + marker stripped; tenant flag off → signal false; marker absent → both false.

**Evidence:** HANDOFF_REQUESTED (historical), `e9b4972` (SHOW_BOOKING_PANEL, #573, 2026-07-23)  
**Estimated time saved:** 20–35 min per new marker (the byte-identical sync step and the "strip-before-render" invariant are the most error-prone parts and the most likely to be skipped)

### 3. `round-iteration-loop`

**Trigger:** A major new feature module (like Agent OS) is being iteratively refined using prod data: each "round" adds fixes, new tests, and metrics, and the pattern repeats. Trigger when commit messages use "Round N:" naming convention or when a `test_suite_roundN.py` file exists and the module has open audit items.

**Pattern observed:** **3 rounds shipped in 7 days** (Rounds 6, 7, 8), each touching the same layer set:

| Layer | Round 6 (`9166b64`) | Round 7 (`e646bdc`) | Round 8 (`970da66`) |
|---|---|---|---|
| New test suite | `test_suite_round6.py` (542 lines) | `test_suite_round7.py` (278 lines) | `test_suite_round8.py` (10 tests) |
| Backend services | `os_web_sources.py`, `voice_call_summary.py` | `voice_phone_routing.py`, `os_constants.py` | `os_opportunity_fulfill.py`, `os_draft_expiry.py` |
| Backend routers | `admin_loop_health.py` (+37L) | `calls_webhooks.py` (new), `auth.py`, MCP server | `admin_loop_health.py` (+65L) |
| Frontend | `ResearchCard.jsx` + test, `BillingPage.jsx` | `ComposerAttachments.jsx`, `os/osStyles.js` (single-source) | `os_email_actions.py` |
| Metrics | `loop_health_scan.py` (+19L) | — | `loop_health_scan.py` (+2L), funnel meters |
| Audit items resolved | R6 items from `audit-enterprise-agent-suites-2026-07-20.md` | M1–M5 from same audit | Dedupe guard, title fallback, sweep fix |

Each round's test suite file mocks Supabase via `backend/tests/fake_supabase.py` (now single-sourced since Round 7 M1).

**Steps the skill would automate:**

1. Read the latest `audits/audit-*.md` file to get the ranked item list. Pick items for this round — max 5 MEDIUM items or 2 HIGH items per round (mixing sizes causes incomplete rounds).
2. Create `backend/tests/test_suite_roundN.py` (N = current max + 1): collect the test contracts for all planned changes BEFORE writing any code (TDD gate). Each service change needs ≥2 test cases.
3. Implement backend changes: services first, then routers, then schema constants. Any constant shared by 2+ modules → extract to `backend/services/os_constants.py` (or domain-equivalent).
4. Frontend: component + test. Check for hardcoded style values or hex colors → extract to the shared styles file (`frontend/src/components/os/osStyles.js` or equivalent).
5. If any metric was silent (owner couldn't see loop health): add the meter to `scripts/loop_health_scan.py` (read the existing structure before adding — the pattern is `Metric: value / threshold`).
6. Run all `test_suite_round*.py` files through pytest to confirm no regressions.
7. Update the audit file: mark resolved items as `[DONE Round N]`.
8. Commit as `Round N: <item summaries> [skip ci]`.

**Evidence:** `9166b64` (Round 6), `e646bdc` (Round 7), `970da66` (Round 8)  
**Estimated time saved:** 15–25 min per round (establishing the round number, remembering the test-suite naming convention, checking fake_supabase for shared helpers, updating the audit file)
