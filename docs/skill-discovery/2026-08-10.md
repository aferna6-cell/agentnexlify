### 1. `route-security-guard-audit`

**Trigger condition:** Any time a new FastAPI billing/payment/account-mutation endpoint is added or an existing one is modified. Also: nightly review flags a missing security dependency on a payment route.

**Steps it would automate:**
1. `grep -rn "block_demo_role" backend/routers/` to get the current guard inventory
2. For each billing/payments/account endpoint missing the guard: add `dependencies=[Depends(block_demo_role)]` + import line
3. Cross-check against pattern in `billing.py:33` (canonical reference)
4. Open `backend/tests/test_plan_gating_new_plans.py` and add a structural assertion that introspects the route's `dependencies` list (pattern: `route.dependencies`, `dep.dependency`, compare to `block_demo_role`)
5. Run `python -c "import ast; ast.parse(open('backend/routers/<file>').read())"` to verify syntax
6. Commit: `fix: add block_demo_role guard to <endpoint>`; then `test: assert block_demo_role guard on <endpoint>`

**Evidence:**

- `c204af2` (2026-08-08) — same fix re-applied correctly after orphaned commits discovered

- The same pattern (add guard → add structural assertion) was executed twice in 48 hours due to the orphaned-HEAD incident. Without a skill, each re-application requires re-discovering the `billing.py:33` reference and the introspection test shape from scratch.

**Estimated time saved:** ~15 min per occurrence. Currently happening at least once per major billing feature (4 routers with the guard in codebase; new routers keep missing it).

### 2. `pr-backlog-triage`

**Trigger condition:** When morning digest or manual inspection reveals 5+ open draft PRs, or when the phrase "PR backlog" or "stale PRs" appears in a digest log.

**Steps it would automate:**
1. List all open PRs (via `mcp__github__list_pull_requests`)
2. Classify each into one of four buckets:
   - **merge-ready** — Dependabot or trivial changes, CI green, no review needed
   - **superseded** — covered by a newer PR (check commit overlap and PR descriptions)
   - **stale-draft** — autonomy-authored, 7+ days old, no recent push → add `needs-review` label
   - **active** — recent push within 3 days, leave alone
3. For merge-ready: merge (Dependabot bump PRs, hotfix PRs with CI green)
4. For superseded: close with a comment explaining which PR supersedes it
5. For stale-draft: add `needs-review` label and post a one-line status comment
6. Write summary to `ops/routines/logs/pr-triage-YYYY-MM-DD.md`

**Evidence:**
- `ops/routines/logs/morning-digest-2026-08-10.md` — 10 open PRs, 6 stale autonomy DRAFTs called out as requiring action
- `ops/routines/logs/morning-digest-2026-08-07.md` — same pattern, 8 open PRs
- The morning digest has flagged this as "Top 3 Priorities" for multiple days running
- Three Dependabot PRs (#629, #630, #631) have been open 7 days and are ready to merge but no skill exists to handle them autonomously

**Estimated time saved:** ~20 min per triage session. Occurs at minimum once per week (more often when autonomy loop is active and generating PRs).

## Existing Skill Updates

### 1. `nightly-commit-review` — Add Detached HEAD Guard

**Problem:** The 2026-08-07 nightly session committed fixes to `billing_usage.py` while running on a detached HEAD (no branch reference). Commits `97e1044`, `cbbaae5`, `7dff08b` were orphaned and never reachable from `refs/heads/main`. The session's own log said "Fixed directly" — accurate about what the session did, wrong about it landing in production. The owner closed GH #640 believing the fix was applied. The 2026-08-08 session had to re-discover and re-apply both fixes.

**Proposed addition** (add to the Pre-Commit section of the skill):
```
# Detached HEAD guard — run before any commit in a scheduled/autonomous session
BRANCH=$(git symbolic-ref HEAD 2>/dev/null)
if [ -z "$BRANCH" ]; then
  git checkout main
  git pull origin main
fi
# After commits, verify:
git symbolic-ref HEAD  # must output refs/heads/main
```

**Evidence:** `c204af2` commit message + `nightly-commit-review-2026-08-08.md` analysis section "Key Finding — Previous Fix Never Merged to Main".

### 2. `feature-build` — Name the Standard 5-File Pattern

**Problem:** The existing `feature-build` skill describes backend steps and frontend steps separately. It does not name or enumerate the canonical 5-file set that every full-stack feature produces. Developers adding features must infer this from examples.

**Proposed addition** (add to the Pre-Build Checklist section):
```
Standard 5-file set for a new feature:
  backend/routers/<feature>.py       — router, registered in main.py
  backend/services/<feature>.py      — service layer
  backend/tests/test_<feature>.py    — pytest tests
  frontend/src/pages/<Feature>.jsx   — React page
  frontend/src/utils/api/<feature>.js — API util

Create all 5 in one atomic commit. If a feature is backend-only or 
frontend-only, name the missing files explicitly as "not needed" in the 
commit message so future reviewers don't hunt for them.
```

**Evidence:** Both `e0e9be6` and `4853c31` follow this exact pattern. When you look at the diffs, the set of file types created is identical even though the feature domains differ completely.
