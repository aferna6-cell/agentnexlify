## Proposed Skills

### 1. `prod-silent-failure-audit`

**Trigger:** User says "something feels off in prod", "metrics seem wrong", or any time a feature has shipped but shows 0 conversion after 2+ weeks. Also trigger when a new plan tier is added.

**Pattern observed:** This exact sequence ran **3 times in a single session** (2026-07-09, PRs #401–#405):

1. **booking_enabled** — column default `false` since migration 005, never set by any insert path → all 3 real tenants had booking silently off for months. Found by auditing the audit.
2. **Voice plan gate** — `MessagingSettingsCards.jsx:496` listed `["professional", "enterprise"]` but backend `_AI_VOICE_PLANS` includes `agent_os`. Current-plan paying customers could never enable voice.
3. **Demo data pollution** — `internal_tenants.py` didn't exclude `(DEMO)` tenants → "9 prod appointments" were 100% demo-seeded. Booking conversion appeared 33%, was actually 0%.

**Steps the skill would automate:**
1. Read `migrations/` for any column with `DEFAULT false` or `DEFAULT null` on a boolean feature flag
2. Cross-reference: does any code insert path explicitly set that column? If not → flag as silent-off risk
3. Read plan gate arrays in frontend JSX and compare to corresponding backend plan sets (grep pattern: `_AI_VOICE_PLANS`, `PLAN_BASELINE_TOKENS`, `planEligible`)
4. Query prod via Supabase MCP: what % of real (non-internal, non-demo) tenants have this flag as the default? If >80% at default → likely never set
5. Write `audits/audit-silent-config-YYYY-MM-DD.md` with findings ranked by revenue impact
6. For each finding: propose 3-layer fix (migration default, code insert, prod backfill)

**Evidence:**
- `dfa8201` — ops-revival, internal_tenants demo exclusion
- `0e0ee00` — booking_enabled fix at 3 layers + migration 163
- `3b30505` — voice plan gate one-line fix found by reading the audit

**Estimated time saved:** 60–90 min per pass (debugging context alone, not including the fix)

### 2. `multi-layer-column-fix`

**Trigger:** When a schema audit or prod measurement reveals a column has the wrong default and real prod data is at the wrong value. Applies when the fix must happen at 3 places simultaneously.

**Pattern observed:** Done **2+ times** this week alone (booking_enabled, business_hours seeding), and the 3-layer fix is what distinguishes a complete fix from a half-migration:

**Steps the skill would automate:**
1. Identify the column, the wrong default, and how many rows in prod are at the bad default
2. Write `migrations/NNN_fix_<column>_default.sql` that: (a) changes the column default, (b) backfills existing rows where safe, (c) adds a CHECK constraint if applicable
3. Update all code insert paths to set the column explicitly (grep for table name in `routers/`, `services/`)
4. Run a targeted prod backfill via Supabase MCP for any existing rows that must change (document the RETURNING count)
5. Write tests: (a) new insert gets the correct value, (b) the "impossible shape" that caused the bug is guarded (e.g., `TestDefaultHoursShape` for the end-before-start hours bug)
6. Update `docs/dev-knowledge/schema-log.md`
7. Write an addendum to the triggering audit file confirming each layer was fixed

**Evidence:**
- `0e0ee00` — booking_enabled DEFAULT false → true; auth.py inserts fixed; migration 163
- `3596009` — `_seed_default_business_hours` for onboarding; impossible-hours shape guarded
- `dfa8201` — renumber duplicate migration 158 → 161; schema-log updated

**Estimated time saved:** 30–45 min per fix (ensuring all 3 layers are covered)

### 3. `gh-actions-revival`

**Trigger:** User reports automation dead or CI failing for 3+ days. Especially when multiple workflows fail at the same time (credential expiry event).

**Pattern observed:** `dfa8201` fixed **4 dead GitHub Actions workflows in one commit** after a credential expiry event on 2026-07-04 took out AUTOPILOT_GH_TOKEN and brain PAT simultaneously. The diagnostic pattern is recognizable and repeatable.

**Steps the skill would automate:**
1. Check recent workflow run history for each workflow in `.github/workflows/` — which ones have >3 consecutive failures?
2. For each failing workflow, check the failure reason: (a) permissions 403, (b) missing secret, (c) expired PAT, (d) scoped permissions block zeroing unlisted scopes
3. For permissions 403: add explicit `permissions:` block to the workflow YAML (pattern: `contents: read`, `issues: write`, `pull-requests: read` — list what the job actually needs)
4. For expired PAT: add preflight validation step + graceful fallback to `github.token`; file a GH issue with human-action-required label
5. For notification channel changes (e.g., Slack → Resend): update the alert script and remove the now-stale secret reference
6. Run a dry-run of each revived workflow (or check next scheduled run)
7. Update `ops/credential-rotation-schedule.md` with next rotation date for any rotated credential

**Evidence:**
- `dfa8201` — refresh-brain.yml permissions, autopilot loop PAT preflight, healthz-alert.sh Slack→Resend
- `ops/credential-rotation-schedule.md` — created this week to prevent recurrence

**Estimated time saved:** 45–60 min per revival session

### 4. `post-deploy-measurement-pass`

It found: lead capture improved 2.5x (validated), real booking conversion was 0% (not 33%), zero signups (traffic is the constraint), and demo data polluting every metric. This entire investigation was manual and took a full session. The weekly funnel report now automates the data pull, but the investigation logic — comparing expected vs actual behavior — is still manual.

**Steps the skill would automate:**
1. Pull funnel metrics from Supabase MCP with `internal_tenants.py` filter applied (exclude demo, internal, is_demo)
2. For each metric, compare to: (a) last measurement, (b) feature intent (e.g., booking nudge should produce booking conversion > 0%)
3. Identify any metric stuck at zero despite a shipped feature → flag as "silent-off" candidate (links to `prod-silent-failure-audit`)
4. Check each real paying tenant's config: booking_enabled, voice_ai_enabled, plan tier vs gated features
5. Write `audits/audit-post-deploy-measurement-YYYY-MM-DD.md` with headline numbers, deltas, and ranked hypotheses
6. For each zero-conversion finding: file a GH issue with `human-action-required` label if cause is unknown, or begin `multi-layer-column-fix` if root cause is clear
7. Update the uptime probe (`ops/monitoring/uptime-checks.json`) with any new semantic assertions uncovered

### 5. `uptime-probe-extend`

**Trigger:** A new production endpoint is added, a silent regression class is discovered, or a new semantic assertion type is needed (e.g., "this key must be non-empty").

**Pattern observed:** The uptime probe in `scripts/monitoring/public_uptime_probe.py` was extended **twice** this week:
- Added `{next_weekday}` URL template expansion (avoid false alarms on weekends for slot-based checks)
- Added `expect_nonempty_key` assertion (catches "200 but slots array is empty" class — exactly the 914 Exterior impossible-hours bug)
- Added 2 new checks to `ops/monitoring/uptime-checks.json`

Each extension followed the same pattern: discover a silent failure class → add a probe capability → add a check → verify against live prod.

**Steps the skill would automate:**
1. Identify the failure class: is it a status-code failure (existing), a JSON shape failure (`expected_json`), or a semantic value failure (`expect_nonempty_key`)?
2. If new failure class: extend `_probe()` in `public_uptime_probe.py` with the new assertion type
3. Add the new check to `ops/monitoring/uptime-checks.json` with: name, url, method, expected_status, and the new assertion key
4. Run the probe locally against prod to verify the new check passes: `python scripts/monitoring/public_uptime_probe.py`
5. For date-dependent URLs: use the `{next_weekday}` template rather than hardcoding a date
6. Commit both the probe extension and the check config together

**Evidence:**
- `3b30505` — `{next_weekday}` template + `expect_nonempty_key` + booking slots check
- `dfa8201` — `www.agentnexlify.com` check added (blind to custom-domain failures)

**Estimated time saved:** 20–30 min per probe extension
