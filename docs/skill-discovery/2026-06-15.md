## Proposed Skills

### 1. `settings-card-add`

**Trigger condition:** User says "add a settings toggle for X", "add settings card for X", "new settings section for X", or when a new backend feature needs a corresponding dashboard settings UI. Also triggers when `SettingsPageContent.jsx` needs a new card.

**Steps it would automate:**

1. Identify the correct card file in `frontend/src/pages/settings/` (Messaging → `MessagingSettingsCards.jsx`, Business → `BusinessSettingsCards.jsx`, etc.)
2. Check `backend/routers/auth.py` `get_tenant` + `update_tenant` to identify the existing settings allowlist — add the new boolean/string field(s) there (input validation if it's a recipient email)
3. Verify the migration already added the column (or flag that migration is needed first)
4. Create the card component in the correct card file — match the toggle/input pattern of adjacent cards in the same file; use `formProps` + `saveProps` spread pattern
5. Import the card in `frontend/src/pages/settings/SettingsPageContent.jsx` and render it in the correct section (pass `handleChange`, `formProps`, `saveProps` as required)
6. If the card introduces a new top-level section/tab, add the section routing in `frontend/src/pages/SettingsPage.jsx`
7. Check `frontend/src/pages/settings/shared.jsx` for any shared input primitives the card can reuse
8. Verify: `npm run build` clean; toggle state correctly reads from and writes to the backend

The pattern is consistent but currently requires reading 3–4 existing cards to understand the `formProps`/`saveProps` spread convention before writing each new one. A skill removes the archaeology and enforces the allowlist update in `auth.py` (missed once in this sprint, caught in a follow-up commit).

### 2. `background-scheduler-service`

**Trigger condition:** User says "add a background job for X", "run X on a schedule", "send X periodically", "sweep X every N minutes", or when a new service needs to run on the existing 5-minute scheduler loop in `backend/main.py`.

**Steps it would automate:**

1. Create `backend/services/<feature>.py` with a single public async function `<verb>_<noun>()` that is the scheduler entry point
2. Implement exactly-once claim pattern when the job has side effects (email send, SMS): use a conditional `UPDATE ... WHERE notified_at IS NULL RETURNING id` to claim rows before processing; release the claim on failure so the next sweep retries
3. Add migration for any new timestamp/flag columns needed (e.g. `notified_at`, `last_triggered_at`) — use a partial index (`WHERE notified_at IS NULL`) for sweep performance
4. In `backend/main.py`, add the import inside the `startup` event handler (lazy import to avoid circular deps):
   ```python
   from backend.services.<feature> import <verb>_<noun>
   ```
   Then add `safe_create_task(<verb>_<noun>())` to the existing scheduled sweep
5. Make the sweep idempotent — if the job runs twice in the same window, it should be a no-op, not a double-send
6. Write tests covering: skip when opt-out flag is false, idle-filter logic, exactly-once claim (second call is no-op), owner email fallback, lost-claim non-send
7. Verify: `python -c "from backend.services.<feature> import <verb>_<noun>"` — import clean

**Evidence:**

| Commit | Service | Exactly-once pattern |
|---|---|---|
| `ca718ab` | `conversation_notify.py` — `notify_idle_conversations()` | `UPDATE conversations SET notified_at = now() WHERE notified_at IS NULL` claim |
| `3f79d7f` | `activation_nudges.py` — `send_activation_nudges()` | claim flag on tenant row |
| `651c6fe` | `widget_health.py` — `refresh_widget_health()` | timestamp sweep with `last_refreshed_at` partial index |

All three followed the same structural pattern: claim → process → release on failure → commit on success. The `safe_create_task` wrapper was used each time to prevent the scheduler from crashing the entire startup if one sweep errors.

**Estimated time saved:** 20–30 min per service. The exactly-once claim pattern is subtle and was re-derived from scratch in at least two of the three implementations. A skill codifies the claim template, the partial-index migration, and the lazy-import convention so developers don't have to reverse-engineer the existing services.

## Existing Skill Updates

### `feature-build` (v1.1.0 → needs v1.2.0)

Two gaps observed this week in the Post-Build section:

1. **`ops/schema/expected-columns.json` not mentioned.** When a migration adds new columns, this JSON file tracks the expected schema for the `schema-sync-check` CI job. It was updated in 4 of the 6 migration PRs this week (`3234597`, `651c6fe`, `3f79d7f`). When developers skipped it, the CI schema-sync check failed on the next PR. Add to Post-Build checklist: `[ ] Update ops/schema/expected-columns.json if new columns were added`.

2. **Adding new test file to `pr-check.yml` pytest selection.** The CI workflow in `.github/workflows/pr-check.yml` maintains an explicit list of test files in the `pytest` call. New test files added this week (`test_integration_health_checker.py`, `test_widget_health.py`, `test_qualifier_config.py`) needed to be added to this list or they silently skipped CI. Add a step: `[ ] If new test file created, add it to the pytest selection in .github/workflows/pr-check.yml`.
