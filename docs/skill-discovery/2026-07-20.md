### 1. `notification-layer-add`

**Trigger:** Any event that fires a backend action (appointment booked, lead captured, appointment rescheduled/cancelled, voice booking, form submission) but does NOT yet notify the owner or customer. Also trigger when a new inbound channel is added (Messenger, form, voice) and the alert parity check reveals a gap.

**Pattern observed:** Done **6 times** in one 3-day window (2026-07-15, PRs #440–#445):

| Commit | What fired | Who notified |
|---|---|---|
| `fc9b36f` (#440) | booking_submit | owner (email + SMS) |
| `f45b05b` (#443) | voice create_appointment | owner (dedup via appointment ID) |
| `9a48ef3` (#442) | staff reschedule/cancel | customer (notice) + reminder re-arm |
| `0907c35` (#444) | staff reschedule/cancel | customer (email + SMS) |
| `07315f6` (#445) | public form + Messenger ingest | owner (first-contact only) |
| `f143de5` (#441) | appointment reminders + automation trigger | bug: wrong status filter — no notifications fired at all |

Every fix followed the same structure: new `backend/services/<domain>_<notify|alerts>.py` implementing email (Resend) + SMS (Twilio) with four invariants always present: (1) dedup by `(tenant, event_id)`, (2) demo-safe (`no-op` for demo tenants via shared denylist), (3) best-effort (`try/except`, never raises, never blocks the primary action), (4) gated on `owner_email` / `notification_phone` + `sms_notifications_enabled`.

**Steps the skill would automate:**
1. Identify the gap: query `docs/dev-knowledge/bug-patterns.md` and commit log for the triggering event — does `send_new_lead_alert`, `send_new_booking_alert`, or an equivalent already fire?
2. Create `backend/services/<domain>_<notify|alerts>.py` with the four invariants (dedup + demo-safe + best-effort + field-gated). Mirror `booking_alerts.py` or `lead_alerts.py` exactly — same `fire_new_<X>_alert_background` helper pattern, `loop.create_task` fallback.
3. Wire the alert into the triggering call site (router or service) with `try/except` wrapper; alert never blocks the primary response.
4. Write 2+ tests: alert fires on new event, dedup suppresses on repeat, demo tenant no-op.
5. If staff action (reschedule/cancel): also check whether `appointment_reminders` rows need re-arming at the new time — see `booking.update_appointment` for the pattern.
6. Update `docs/dev-knowledge/bug-patterns.md` if this was a silent gap.

**Evidence:** `fc9b36f`, `f45b05b`, `9a48ef3`, `0907c35`, `07315f6`, `f143de5` (PRs #440–#445)

**Estimated time saved:** 25–40 min per notification addition (getting the four invariants right, avoiding double-fire, handling the `loop.create_task` fallback correctly for sync callers)

### 2. `digest-job-add`

**Trigger:** A new automated health check or monitoring metric needs a daily push alert (not a pull API). Also trigger after any new background loop is added — the loop needs a watcher that pages when it stalls.

**Pattern observed:** Done once (`03a682c`, PR #464) followed immediately by **2 bug fixes** that reveal the pattern is non-obvious:

- `26f7829` (#468): every digest job used the Supabase anon key (`SUPABASE_SERVICE_KEY` secret held the anon key after a credential rotation). Anon key + RLS → all queries return empty silently. Every health check reported "healthy" against zero rows. Fix: a "blind state" guard — a real deployment always has tenants, so zero tenant rows short-circuits all other rules and emits a `BLIND` alert naming the misconfiguration. Without this guard, a misconfigured secret is invisible and production looks green.
- `6391bd3` (#469): the workflow job never declared `permissions: issues: write` → `GITHUB_TOKEN` was read-only → every `gh issue create` step 403'd silently. This is the same class of bug that hit `gh-actions-revival` (proposed 2026-07-13).

The pattern, once correct, is: standalone Python script in `scripts/` with an injectable fetcher (so tests run without network), added as a new job in `.github/workflows/daily-business-digest.yml` (not a new workflow file — the digest workflow is the canonical home), with `permissions: issues: write` declared at job level.

**Steps the skill would automate:**
1. Create `scripts/<name>_scan.py` with pure functions: `collect_vitals(fetch)`, `evaluate_alerts(vitals)`, `render_report(alerts, vitals)`, `summarize(report)`. Injectable `fetch` arg — no hardcoded HTTP calls.
2. Include the **blind-state guard** as the first `evaluate_alerts` check: zero tenants → emit `BLIND` alert immediately; skip all other rules. Comment: "Supabase anon key returns empty on RLS tables; zero tenants = misconfigured credentials, not a healthy deployment."
3. Add a corresponding test file `backend/tests/test_<name>_scan.py` (or `tests/test_<name>_scan.py`): blind state fires one alert with "service_role" in the message; real-alert condition fires with tenant name; quiet state produces no alerts.
4. Add a new job to `.github/workflows/daily-business-digest.yml` with:
   - `permissions: contents: read; issues: write` (always both — read for checkout, write for issue filing)
   - Supabase REST calls using `${{ secrets.SUPABASE_URL }}` + `${{ secrets.SUPABASE_SERVICE_KEY }}`
   - Deduped issue filing (grep open issues for a unique tag before creating a new one)
5. Cross-ref the interactive pull endpoint: if a GET `/api/v1/admin/<name>` endpoint exists for the same vitals, link to it in the job output log. Push (job) + pull (endpoint) are complementary.

**Evidence:** `03a682c` (PR #464), `26f7829` (PR #468), `6391bd3` (PR #469)

**Estimated time saved:** 45–75 min per new monitoring job (the blind-state guard alone cost one full debugging session; the permissions bug is recurring)

### 3. `agent-os-extension`

**Trigger:** Adding a new capability to the Agent OS module — anything that surfaces in `/agent-os` dashboard, runs as a background task (opportunity scan, research worker, draft expiry), or bridges with an inbound channel (widget, Messenger, voice). Trigger when a task description includes "agent", "opportunity", "deliverable", "suggestion", or "os_" in the context of the AgentOS feature set.

**Pattern observed:** **9 commits** in one week (PRs #446–#462, all `feat(agent-os):`) all follow an identical file structure:

| Layer | File pattern | Purpose |
|---|---|---|
| Backend service | `backend/services/os_<name>.py` | Core logic: DB reads, Claude API calls, decision trees |
| Backend test | `backend/tests/test_os_<name>.py` | Unit + integration tests, mocked Supabase |
| Frontend component | `frontend/src/components/os/<Name>.jsx` + `<Name>.test.jsx` | Dashboard card/panel |
| Page wire-in | `frontend/src/pages/AgentOS.jsx` | Import + render the component |
| Main wire-in | `backend/main.py` | `app.include_router(os_<name>.router)` if new router |

Examples: `os_opportunities.py` + `OpportunityCards.jsx`, `os_draft_expiry.py` + `DeliverablePanel.jsx` badge, `os_inbound_bridge.py` + `SettingsInboundChannels.jsx` wiring.

**Steps the skill would automate:**
1. Define the capability: what does the background service decide, and what does the dashboard surface?
2. Create `backend/services/os_<name>.py`: pure functions where possible, injectable Supabase client for testing, best-effort (never raises to caller).
3. If new router: `backend/routers/os_<name>.py` → register in `main.py` (see lines 746–813).
4. Create `backend/tests/test_os_<name>.py`: mock Supabase, test the decision branches and alert conditions.
5. Create `frontend/src/components/os/<Name>.jsx`: follow `OpportunityCards.jsx` pattern — loading/error/empty states, admin-secret prompt if needed.
6. Add `<Name>.test.jsx` asserting the rendered card before testing click behavior (rule: assert observable output before testing interactions).
7. Wire into `frontend/src/pages/AgentOS.jsx`: import + render in the appropriate section.
8. Run `npm run build` clean + verify no TypeScript/lint errors.
9. Run `backend/tests/test_os_<name>.py` via pytest.

**Evidence:** `a8eebf9` (#462), `876bd4a` (#461), `93133ec` (#460), `79f45cf` (#458), `eedbc53` (#457), `7eadaba` (#456), `f693c0b` (#449), `fc33c05` (#448), `ae082b0` (#446)

**Estimated time saved:** 15–25 min per feature (eliminating the "which files, in what order?" lookup; catching the test-assertion order mistake before it fails review)
