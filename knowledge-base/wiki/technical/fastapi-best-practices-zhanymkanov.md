# FastAPI Best Practices — Domain-Module Structure, Async Discipline, and Pydantic Patterns

Zhanymkanov's FastAPI best-practices repo has become the de-facto production FastAPI reference — tested against Python 3.11+, FastAPI 0.115+, Pydantic 2.7+, SQLAlchemy 2.0+, and Alembic 1.13+. The three load-bearing recommendations are: (1) organize by domain module, not file type, inspired by Netflix Dispatch; (2) take async-vs-sync route discipline seriously because misuse silently tanks throughput; (3) push validation aggressively into Pydantic and dependency functions so routes become thin orchestration layers. For AgentNexLiFy's FastAPI backend — which currently has 57 agents, 30+ routers, and a growing set of Pydantic models wired into Supabase — these patterns map onto real file-structure and code-review decisions already accumulating in `backend/`.

The project structure guidance directly contradicts the common "src/{routers,schemas,services}" layout. Instead, each domain (auth, posts, aws) gets its own folder with its own `router.py`, `schemas.py`, `models.py`, `service.py`, `dependencies.py`, `constants.py`, `exceptions.py`, `utils.py`, and `config.py`. Cross-domain imports use explicit module names (`from src.auth import constants as auth_constants`) to avoid collision. This scales to monolith-sized codebases because the cognitive unit stays at the domain, not the file-type. For AgentNexLiFy the existing `backend/routers/` pattern sits somewhere between: routers are separated but schemas, services, and dependencies still live in shared directories. A future refactor toward domain-module structure would pay off most in areas already showing coupling pain (widget, chat, automation).

Async discipline is the pattern most likely to silently corrupt throughput. FastAPI runs `sync` routes in a threadpool; `async` routes run on the event loop. A blocking call inside an `async` route (e.g., `time.sleep`, requests.get, a sync DB driver) will block the entire event loop, not just the coroutine — every concurrent request waits. Three signatures matter: `async def` with `await asyncio.sleep()` (ideal), `def` that blocks (acceptable — runs in threadpool), `async def` that blocks (terrible — kills the server). AgentNexLiFy's `main.py` uses async routes, so any sync Anthropic SDK call, sync Supabase client call, or blocking file read inside an async handler is a latent throughput bug. The repair pattern is `run_in_threadpool` from Starlette: `await run_in_threadpool(sync_client.make_request, data)`. CPU-bound work needs a task queue (Celery/Arq/RQ); the threadpool doesn't save you because of the GIL.

Pydantic should carry most data validation, not routes. The `excessively use Pydantic` rule applies built-in validators (regex, EmailStr, Field constraints, StrEnum, AnyUrl) before custom code. A `CustomModel` global base lets the whole app enforce datetime serialization format, timezone handling, and a `serializable_dict()` method consistently. `BaseSettings` should be split per domain (`auth_settings`, `config.settings`) rather than a single monolithic settings object that accumulates every env var. This matches the CLAUDE.md note that `from __future__ import annotations` breaks Pydantic resolution in FastAPI files — Pydantic must see real types, not stringified deferred annotations, and this repo's patterns assume that as a baseline.

Dependencies are the FastAPI feature most under-used as a validation layer. The canonical pattern: a `valid_post_id` dependency that fetches the post by id and raises `PostNotFound` if missing, then every route that takes `post_id` depends on it and receives the post dict directly. Chaining works transparently — `valid_owned_post` depends on `valid_post_id` and `parse_jwt_data`, both of which are cached per-request so repeated calls don't duplicate work. This turns routes into three-line orchestrations and centralizes "does this resource exist and does this user own it?" logic in one place. For AgentNexLiFy's tenant-isolation pattern (every request scoped by `client_id` per CLAUDE.md's Critical Rule 1), a `valid_tenant_scoped_resource` dependency would enforce the invariant once rather than leaving it to every handler.

Several micro-patterns catch common mistakes. Async dependencies are preferred over sync because sync dependencies still pay threadpool overhead even when the work is trivial. `BackgroundTasks` is fine for fire-and-forget sub-second work (send a welcome email) but a footgun for anything retry-worthy or multi-second — use Celery/Arq/RQ instead, with the rule-of-thumb "if you'd page someone when the task is lost, it doesn't belong in BackgroundTasks." `ValueError` raised inside a Pydantic `field_validator` surfaces to the client as a structured 422, which gives free input validation error responses when used inside request-body schemas. Alembic migrations should be descriptive and follow naming conventions; SQL-first thinking before Pydantic; use `ruff` for linting.

REST conventions reduce dependency duplication. Two routes `/profiles/{profile_id}` and `/creators/{creator_id}` that both validate the profile exists should share the path variable name (`profile_id`) and chain `valid_creator_id` on top of `valid_profile_id` — not duplicate the existence check. Response serialization gotcha: Pydantic models passed as return values get serialized twice (once by your code, once by FastAPI for `response_model` validation), so returning a dict from a route with `response_model=Schema` skips the first construction. This is a minor perf win but matters in hot-path endpoints.

## Key Concepts

- **Domain-module structure** — Organize `src/` by business domain (auth, posts, billing), each with router/schemas/models/service/dependencies — not by file type (all routers in one folder). Inspired by Netflix Dispatch.
- **Threadpool offload** — FastAPI runs `sync def` routes in a threadpool so they don't block the event loop; `async def` routes run on the loop directly. Blocking calls in `async def` stall every concurrent request.
- **Dependency-as-validation** — Use `Depends(valid_resource_id)` to fetch and validate existence, permissions, and ownership once; routes receive the validated resource rather than re-validating.
- **Per-request dependency caching** — FastAPI caches dependency results within a single request, so the same `parse_jwt_data` called from three chained dependencies executes only once.
- **BackgroundTasks vs task queue** — `BackgroundTasks` for in-process fire-and-forget under 1 second; Celery/Arq/RQ for retries, scheduling, rate-limiting, or multi-second work.
- **ValueError → ValidationError** — Raising `ValueError` in a Pydantic `field_validator` surfaces as a structured 422 response, giving free client-side validation errors for request bodies.

## Relevance to AgentNexLiFy

Three actionable bets. First, audit every `async def` route in `backend/routers/` for blocking calls — Anthropic SDK sync calls, Supabase client sync calls, and file I/O in non-test code are the three most likely offenders. Each one caught and converted via `run_in_threadpool` improves throughput under concurrency, and the fix is mechanical enough to delegate to Haiku per `.claude/rules/model-routing.md`. Second, consolidate the per-tenant validation pattern into a named dependency (e.g., `valid_tenant_scoped_lead`) that enforces CLAUDE.md's Critical Rule 1 (`client_id not tenant_id`) once, and make it the only place that checks — today the check is scattered across routers and is exactly the bug surface the guide warns against. Third, the domain-module restructure is a longer-term play but the first clean split is probably the `widget/` and `chat/` domains, which already have their own routers, services, and Pydantic models spread across shared directories — collapsing them into self-contained domain folders would make both easier to refactor in isolation. This aligns with `user-rules.md` Rule 9 (factor god classes) and Rule 12 (new files over bloat).
