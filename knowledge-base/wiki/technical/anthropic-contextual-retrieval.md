# Contextual Retrieval — Reducing RAG Failure Rates by 67%

Traditional RAG systems split documents into chunks for efficient retrieval, but this chunking destroys the context that makes each chunk meaningful. A chunk reading "The company's revenue grew by 3% over the previous quarter" is useless without knowing which company, which quarter, or what the baseline was. Anthropic's Contextual Retrieval solves this by prepending chunk-specific explanatory context before embedding and BM25 indexing — a preprocessing step that reduced retrieval failure rates by 49%, and by 67% when combined with reranking. For AgentNexLiFy's tenant knowledge base system, which uses [[pgvector-postgres-vector-search]] for semantic search across FAQ and business documents, this technique directly addresses the retrieval accuracy gap that causes the chat widget to miss relevant answers.

The method has two sub-techniques. **Contextual Embeddings** prepend a short context passage (50-100 tokens) to each chunk before generating the embedding vector. The context explains what the chunk is about within the broader document — for an SEC filing, a chunk about 3% revenue growth gets prefixed with "This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million." This context is generated by Claude using a simple prompt that passes the whole document and asks for a succinct situating passage. **Contextual BM25** applies the same contextual prefix before building the BM25 (lexical matching) index, improving exact-match retrieval alongside semantic search.

The cost model is remarkably efficient thanks to prompt caching. The reference document is loaded into the cache once, and each chunk's context generation reuses the cached document. At 800-token chunks, 8K-token documents, 50-token instructions, and 100 tokens of context per chunk, the one-time preprocessing cost is $1.02 per million document tokens. This makes Contextual Retrieval feasible even for large knowledge bases — a key consideration since AgentNexLiFy tenants may upload hundreds of pages of FAQs, service descriptions, and pricing sheets. The prompt caching integration described here uses the same mechanics documented for the chat widget's system prompt in production use.

Performance results across codebases, fiction, ArXiv papers, and science papers were consistent. Contextual Embeddings alone reduced top-20-chunk retrieval failure rate by 35% (5.7% → 3.7%). Combining Contextual Embeddings with Contextual BM25 achieved a 49% reduction (5.7% → 2.9%). Adding a reranking step (using Cohere's reranker, though Voyage also offers one) pushed the improvement to 67% (5.7% → 1.9%). The results were measured using 1 minus recall@20, and the improvements held across all embedding model and source domain combinations tested. Voyage and Gemini embeddings performed best, consistent with the [[pgvector-implementation-guide]] recommendation for production embedding selection.

Several implementation details matter. Chunk boundaries — size, overlap, and splitting strategy — significantly affect retrieval performance and should be tuned per use case. Delivering the top-20 chunks outperformed top-10 or top-5 in testing, though more chunks can distract models, so the optimal count depends on the task. Custom contextualizer prompts tailored to the specific domain (including glossaries of terms defined elsewhere in the knowledge base) can outperform the generic prompt. Response generation may improve when the model receives the contextualized chunk with clear markers distinguishing context from original content.

The post also notes that for knowledge bases under 200,000 tokens (~500 pages), the simplest solution is to include the entire knowledge base in the prompt and use prompt caching to make this cost-effective. Prompt caching reduces latency by >2x and costs by up to 90% for cached prefixes. This "just stuff it in the prompt" approach should be the first option evaluated before implementing RAG, a principle that aligns with the simplicity-first philosophy in [[llm-wiki-karpathy-pattern]].

Reranking adds a filtering step between initial retrieval and final prompt injection. The initial retrieval returns ~150 candidate chunks, a reranking model scores each for relevance to the query, and only the top-K (typically 20) are passed to the generative model. This reduces noise, cost, and latency from processing irrelevant chunks. The tradeoff is additional latency from the reranking step itself, though rerankers score chunks in parallel. The key finding is that all techniques stack: contextual embeddings + contextual BM25 + reranking + top-20 chunks delivers maximum performance.

## Key Concepts

- **Contextual Embeddings** — Prepending chunk-specific explanatory context (50-100 tokens) before generating the embedding vector, ensuring the embedding captures the chunk's meaning within its broader document context.
- **Contextual BM25** — Applying the same contextual prefix to chunks before building the BM25 lexical index, improving exact-match retrieval for specific identifiers and technical terms.
- **BM25 (Best Matching 25)** — A ranking function using lexical matching to find precise word or phrase matches. Builds on TF-IDF with document length normalization and term frequency saturation. Complements semantic embeddings for exact-match queries like error codes.
- **Reranking** — A post-retrieval filtering step where a specialized model scores candidate chunks for relevance to the query, keeping only the top-K most relevant. Adds latency but significantly improves precision.
- **Retrieval failure rate** — Measured as 1 minus recall@K: the percentage of relevant documents that fail to appear in the top-K retrieved chunks. The primary metric for evaluating retrieval quality.

## Relevance to AgentNexLiFy

AgentNexLiFy's tenant knowledge base pipeline (`backend/services/tenant_kb.py`, `backend/routers/tenant_kb.py`) chunks uploaded documents and stores embeddings in the `kb_articles` table via pgvector. As of PR #471 (2026-07-17), two of the three Contextual Retrieval techniques are now live behind feature flags: `backend/services/kb_reranker.py` adds a Haiku-based reranking pass after initial vector/FTS retrieval (gated by `widget_kb_rerank_enabled`), and `backend/services/kb_hybrid_retrieval.py` merges FTS results alongside semantic results to catch exact keyword matches the embedding misses (gated by `widget_kb_hybrid_enabled`). Both flags are seeded to `'1'` in the `platform_settings` table (migration 175, PR #476) for the pilot — they can be flipped without a Railway deploy. The remaining gap is the contextual embedding step itself: chunks are still embedded without situating context prefixes, which is the primary technique in this paper. Implementing contextual prefixes in the ingestion pipeline would compound on top of the existing reranking + hybrid gains and drive retrieval failure toward the paper's 1.9% floor. For tenants with small knowledge bases (<500 pages), the prompt-stuffing approach with prompt caching should be evaluated first — it eliminates retrieval failures entirely at the cost of higher per-request token usage, which may be acceptable for tenants with compact FAQs.
