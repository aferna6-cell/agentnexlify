# Claude Code Best Practices — Anthropic's Official Engineering Playbook

Anthropic's engineering guide for Claude Code collapses into one root constraint and five operating levers. The constraint: every conversation, file read, and command output competes for a finite context window, and model performance degrades as that window fills. Earlier instructions get "forgotten," mistakes compound, and the session silently drifts. Every other best practice derives from managing that resource. The five levers are verification criteria, separation of planning from implementation, prompt specificity, CLAUDE.md hygiene, and permission discipline — each designed to push work out of the context window or make what remains inside the window carry more signal.

The single highest-leverage practice is giving Claude a way to verify its own output. Provide tests, screenshots, or expected outputs so the model can check itself — without verification criteria, Claude produces work that looks right but fails quietly, and the human becomes the only feedback loop. The canonical examples in the guide are surgical: replace "implement a function that validates email addresses" with "write a `validateEmail` function. example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing." Replace "make the dashboard look better" with "[paste screenshot] implement this design. take a screenshot of the result and compare it to the original. list differences and fix them." Replace "the build is failing" with "the build fails with this error: [paste]. fix it and verify the build succeeds. address the root cause, don't suppress the error." UI work benefits from the Claude in Chrome extension, which opens browser tabs, tests the UI, and iterates until the code works. This maps directly onto AgentNexLiFy's [[autonomous-webapp-test|Playwright-backed verification workflow]].

Plan Mode separates research and planning from implementation so the model doesn't solve the wrong problem. The recommended four-phase workflow: (1) enter Plan Mode, direct Claude to read relevant files and answer questions without making changes; (2) ask for a detailed implementation plan, then press Ctrl+G to open it in a text editor for direct edits before execution; (3) switch back to Normal Mode and let Claude code, verifying against its plan; (4) commit with a descriptive message and open a PR. Plan Mode adds overhead, so skip it when the scope is clear and the fix is small — typos, log lines, variable renames. Plan Mode pays off when the change modifies multiple files, when the approach is uncertain, or when the code being modified is unfamiliar. The rule of thumb: if you could describe the diff in one sentence, skip the plan. This is the same threshold that gates the `ultrathink.md` plan-mode rule and the `grill-me` skill in the daily-skills loop.

Prompt specificity is the lever that most underperforms in practice. Four patterns dominate. **Scope the task** — "add tests for foo.py" becomes "write a test for foo.py covering the edge case where the user is logged out. avoid mocks." **Point to sources** — "why does ExecutionFactory have such a weird api?" becomes "look through ExecutionFactory's git history and summarize how its api came to be." **Reference existing patterns** — "add a calendar widget" becomes "look at how existing widgets are implemented on the home page. HotDogWidget.php is a good example. follow the pattern to implement a new calendar widget that lets the user select a month and paginate forwards/backwards to pick a year. build from scratch without libraries other than the ones already used in the codebase." **Describe the symptom** — "fix the login bug" becomes "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it." Vague prompts still have a place — "what would you improve in this file?" surfaces things you wouldn't have thought to ask — but only when you can afford to course-correct. This maps onto the `[ROLE] + [TASK] + [CONTEXT] + [CONSTRAINTS] + [OUTPUT]` formula in `.claude/rules/prompt-formula.md`.

CLAUDE.md is the persistent context file Claude reads at the start of every conversation — run `/init` to generate a starter based on current project structure, then refine. The guide is specific about what belongs and what doesn't. Include Bash commands Claude can't guess, code style rules that differ from defaults, testing instructions and preferred test runners, repository etiquette (branch naming, PR conventions), architectural decisions specific to the project, developer environment quirks (required env vars), and common gotchas. Exclude anything Claude can figure out by reading code, standard language conventions, detailed API documentation (link to docs instead), information that changes frequently, long explanations or tutorials, file-by-file descriptions, and self-evident practices like "write clean code." The hard-won warning: bloated CLAUDE.md files cause Claude to ignore your actual instructions. If Claude keeps doing something you don't want despite a rule against it, the file is probably too long and the rule is getting lost. Prune regularly; test changes by observing whether behavior actually shifts. For each line, ask "would removing this cause Claude to make mistakes?" — if not, cut it. Emphasis like "IMPORTANT" or "YOU MUST" can improve adherence for critical rules. Domain knowledge that's only relevant sometimes belongs in skills (loaded on demand), not CLAUDE.md (loaded every session).

CLAUDE.md supports imports via `@path/to/import` syntax and can live at multiple scopes: `~/.claude/CLAUDE.md` (all sessions), `./CLAUDE.md` (project, checked into git), `./CLAUDE.local.md` (personal project-specific, gitignored), plus parent and child directories that Claude pulls in on demand. Data input is flexible — reference files with `@` so Claude reads before responding, paste images via copy/paste or drag-and-drop, provide URLs for documentation (allowlist via `/permissions`), pipe data with `cat error.log | claude`, or let Claude fetch what it needs via Bash, MCP, or file reads. Permission management reduces the constant approval prompts that cause reviewers to click through without reviewing. Three mechanisms: **auto mode** routes approvals through a separate classifier model that blocks only scope escalation, unknown infrastructure, or hostile-content-driven actions; **permission allowlists** permit specific safe commands like `npm run lint` or `git commit`; **sandboxing** enables OS-level isolation of filesystem and network. AgentNexLiFy already applies the Trail of Bits hardening pattern documented in [[claude-code-security|claude-code-security.md]], combining all three.

CLI tools are the most context-efficient way to interact with external services. Install `gh`, `aws`, `gcloud`, `sentry-cli`, and similar — without them, Claude falls back to authenticated API calls that often hit rate limits. Claude is also effective at learning unfamiliar CLIs on demand: `Use 'foo-cli-tool --help' to learn about foo tool, then use it to solve A, B, C.`

## Key Concepts

- **Context window degradation** — The observed performance drop as the context fills. Earlier instructions get "forgotten," error rates rise, and drift compounds silently. The root constraint all best practices address.
- **Verification criteria** — Tests, expected outputs, screenshots, or Bash commands that let Claude check its own work. The single highest-leverage lever because it removes the human as the only feedback loop.
- **Plan Mode** — Claude Code mode where the model reads and answers without making changes. Used before implementation for uncertain or multi-file work; skipped when the diff fits in one sentence.
- **Permission modes** — Three mechanisms (auto mode, allowlists, sandboxing) that reduce approval friction while keeping safety boundaries. Auto mode uses a classifier to approve routine commands and escalate risky ones.
- **CLAUDE.md hygiene** — The discipline of keeping project instructions short and human-readable. Bloated files cause Claude to ignore instructions; the test is "would removing this cause Claude to make mistakes?"

## Relevance to AgentNexLiFy

The playbook validates the architecture already in place: a lean top-level CLAUDE.md that references rule files rather than duplicating them, a skills directory for on-demand loading, and hooks that enforce hard rules deterministically. The immediate work is auditing CLAUDE.md against the "would removing this cause Claude to make mistakes?" test — at current length the risk of rule dilution is real, and pruning low-signal lines is higher-ROI than adding new ones. The second opportunity is tightening verification criteria on every feature task: the `/new-feature` skill should require explicit test cases or screenshots in the prompt before execution, matching the guide's "address root causes, not symptoms" pattern. Third, widen CLI adoption — `gh` and Supabase MCP are already wired, but Sentry and Railway operations still route through the UI more than the CLI, which burns context unnecessarily. The permission-mode section maps cleanly onto the existing deny/ask/sandbox config — no changes needed there, but the auto-mode classifier is a future win for long autonomous loops like the nightly commit review.
