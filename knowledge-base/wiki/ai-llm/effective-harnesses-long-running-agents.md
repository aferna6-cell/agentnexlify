# Effective Harnesses for Long-Running Agents — Initializer + Coding Agent Pattern

Long-running agents fail in predictable ways when a single general-purpose harness runs in a loop across multiple context windows. Even Opus 4.5 on the Claude Agent SDK, with compaction enabled, could not reliably build a production-quality web app from a single high-level prompt. Anthropic's April 2026 engineering post documents two dominant failure modes and a two-part harness that addresses both: a specialized initializer agent that runs once to stand up the environment (feature-list JSON, `init.sh`, `claude-progress.txt`, initial git commit) and a coding agent that runs every subsequent session with a different prompt, asking it to make incremental progress and leave a clean state. The practical lesson is that context-window limits aren't fixed by more context — they're fixed by a harness that teaches the model how to reconstitute state on a cold start.

The first failure mode is the one-shot attempt. A model given a high-level spec ("build a claude.ai clone") tries to implement everything at once, runs out of context mid-implementation, and leaves the next session with a feature half-built and undocumented. The next agent then spends its budget guessing at what happened and patching broken basics. Compaction helps but doesn't eliminate this — compacted instructions pass imperfectly to the next agent. The initializer's answer is the feature list: a structured JSON file with 200+ end-to-end feature descriptions (each with a category, description, reproduction steps, and a `passes: false` flag). JSON is chosen over Markdown because the model is less likely to inappropriately rewrite JSON, and coding agents are constrained by prompt to change only the `passes` field. The instruction is written in strong terms — "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality."

The second failure mode is premature victory. Later in a project, a coding agent looks around, sees progress has been made, and declares the job done. The feature list closes this by giving every session an explicit inventory of unfinished work. The coding agent's prompt directs it to read the feature list at session start, pick the highest-priority incomplete feature, and work on exactly that one feature — not batch progress across many. Incremental progress, not volume, is the explicit goal. Combined with end-of-session git commits and a written progress summary in `claude-progress.txt`, this lets each new agent reconstruct what happened without having to infer it from code diffs alone. This is the same context-reconstruction insight that underpins the 15-message handoff summary rule in this project and that [[claude-code-best-practices]] codifies as CLAUDE.md hygiene.

Testing is the third failure mode Anthropic calls out. Claude had a tendency to mark features "complete" after unit tests or `curl` smoke-checks without verifying end-to-end. The fix was explicit prompting to use browser automation tools and test as a human user — in the demo, every coding agent used the Puppeteer MCP to start a new chat, send a message, and verify a response before starting new work. The architecture mirrors [[anthropic-building-effective-agents]]'s evaluator-optimizer pattern: the agent is both builder and acceptance tester, with browser automation providing the ground truth the model can't infer from code alone. Anthropic acknowledges limitations — browser-native alert modals aren't visible through Puppeteer, so features relying on them stayed buggier — which matches AgentNexLiFy's widget-test skill caveat that cross-origin iframe state requires real-browser verification, not snapshot-only checks.

The "get up to speed" ritual is the harness's operational core. Every coding agent session starts with the same sequence: `pwd` to confirm working directory, read `claude-progress.txt` and git log for recent work, read the feature list and pick the next highest-priority incomplete feature, run `init.sh` to start the dev server, and smoke-test basic functionality through the browser automation tool before writing any new code. This saves tokens (the agent doesn't have to figure out how to test), catches regressions from earlier sessions before they compound, and anchors the agent to a known-working baseline. A typical session transcript reads as a fixed opening of `pwd → read progress → read feature list → git log → init.sh → browser smoke test → pick feature → implement`. The pattern is close to the advisor-executor split AgentNexLiFy uses per [[claude-opus-4-7-release]] — the initializer is a one-time advisor producing durable artifacts, the coding agent is the per-session executor.

The open questions Anthropic flags are worth noting. First, whether a single general-purpose coding agent is optimal or whether specialized sub-agents (testing, QA, cleanup) would outperform — the article leans toward multi-agent as the likely next step. Second, whether the harness generalizes beyond full-stack web app development to scientific research or financial modeling. For AgentNexLiFy the analogous generalization question is whether the initializer + coding pattern transfers to tenant-facing agentic work — not coding, but lead qualification, appointment booking, or content generation — where "feature list" becomes "service catalog" and "progress file" becomes "session transcript." The abstractions are the same; the surfaces differ.

## Key Concepts

- **Initializer Agent** — Agent that runs only on the first session with a specialized prompt to set up environment scaffolding (feature list, init script, progress file, initial git commit). Produces durable artifacts the coding agent consumes.
- **Coding Agent** — Agent that runs every subsequent session with a different prompt, works on exactly one feature at a time, and leaves a clean git-commit and progress-summary state at session end.
- **Feature List** — Structured JSON file with every end-to-end feature required by the spec, each marked `passes: false` initially. Coding agents may only update the `passes` field, never add or remove features.
- **Progress File** (`claude-progress.txt`) — Append-only running log of what each session worked on. Read at session start, written at session end. Bridges context-window boundaries.
- **Clean State Rule** — Session-end invariant: no major bugs, orderly code, enough documentation that a new developer could pick up new work without cleanup. Prevents failure cascades across sessions.
- **Incremental Progress Prompt** — Explicit instruction pattern that limits each session to one feature, preventing the one-shot-attempt failure mode.

## Relevance to AgentNexLiFy

This harness is directly applicable to two AgentNexLiFy subsystems. First, the nightly commit review and the issue-to-PR loop (per `.claude/skills/issue-to-pr-loop/SKILL.md`) are de facto long-running agents today, running on a 15-minute cadence without an initializer-coding split. Adopting the pattern means writing an initializer session per issue that materializes a `feature_list.json` (or equivalent issue-checklist), an `init.sh` that restarts the backend/frontend dev servers, and a progress file — and then constraining the per-cadence agent to pick one unchecked item per session. The expected win is fewer declared-done-early issues and fewer broken-baseline sessions. Second, the same pattern applies to tenant-facing managed agents where "feature list" becomes a per-tenant service catalog and "progress file" becomes the conversation transcript summary — session durability isn't just Anthropic-infra, it's a prompt-discipline pattern we can implement client-side. The immediate ROI is on the internal development harness; the tenant-facing application is a follow-on experiment.
