Prompt caching prices a repeated prefix at roughly a tenth of standard input cost after one full-price write. That ratio is well documented; what this source adds is measured production outcomes across three different workload shapes — a support chatbot, a code review agent, and a research assistant — landing at 65%, 71%, and 60% monthly savings respectively, with two to four hours of implementation each. The mechanism is unglamorous: the cache is keyed on the exact bytes of the cached portion plus the model version, so most of the engineering is making a prompt prefix byte-stable across requests. Every failure mode in the source is a prompt-construction bug, and each one is cheap to fix once measured.

The pricing has two knobs. A 5-minute TTL costs 1.25x base input to write and 0.1x to read; a 1-hour TTL costs 2x to write and the same 0.1x to read. Break-even is three reads inside the 5-minute window or five reads inside the hour — below that the write premium exceeds the read discount and caching loses money. That arithmetic decides TTL per surface rather than per application. Most production systems combine both: 1-hour TTL on static prefixes like system prompts, tool schemas, and retrieved documents, and 5-minute TTL on conversation history that turns over quickly. [[claude-prompt-caching-5min-ttl-2026]] covers the shorter window's refresh-on-hit behavior in more detail, and [[claude-prompt-caching-cost-optimization-kissapi]] works through the same pricing table from an API-integration angle.

Five patterns carry nearly all of the savings. Large system prompts are the highest-leverage single change: a 4,000-token system prompt costs $0.012 per request uncached at Sonnet rates and $0.0012 cached, which is roughly $108/day at 10,000 daily requests and about five times that on Opus. RAG context is the second: retrieved documents run 5,000-30,000 tokens and usually stay fixed across a multi-turn exchange, so a 10-turn conversation carrying 30,000 tokens of context drops from 300,000 input tokens ($0.90) to 57,000 effective tokens ($0.175). Conversation history caching, marked on the last message before the current turn, roughly halves input cost for long-running conversational agents. Tool definitions consume 3,000-8,000 tokens of schema per request and are cached automatically once a `cache_control` block appears in the system prompt, worth 40-70% on agent workloads. Few-shot example blocks round out the list because they rarely change.

The measured cases show how those patterns stack. The customer support chatbot ran 50,000 requests/day on Sonnet 4.6 with a 3,200-token system prompt, 15,000 tokens of knowledge-base context, and 600 tokens of user input, moving from $8,820/mo to $3,105/mo. The code review agent handled 800 PRs/mo on Opus 4.6 across four cached segments and fell from $2,190/mo to $642/mo — the highest percentage of the three, because Opus input pricing makes every avoided full-price token worth five times more. The research assistant ran 10,000 sessions/mo averaging 4.5 turns with history growing to 40,000 tokens, dropping $4,140/mo to $1,650/mo. Two facts hold across all three: the win scales with prefix size times request volume, and it scales with the price of the model whose input you are avoiding.

Five anti-patterns account for the misses. Timestamps embedded in cached content invalidate the prefix on every single request; truncate to day precision or move the field outside the cached block. User-specific content in the prefix ("You are helping {user.name} at {user.company}") produces one cache miss per user, which is the same as no caching for a wide user base. Inconsistent prompt construction — stray whitespace, reordered sections, variable interpolation that sometimes emits a trailing newline — accounts for roughly 80% of needless misses, and normalizing the builder function fixes it. Model version migrations invalidate every cache, so warmup belongs in the upgrade plan rather than being discovered from a billing spike. And prefixes below the minimum cacheable length (1,024 tokens on Sonnet, 2,048 on Opus) silently do not cache at all; `cache_creation_input_tokens` returning zero is the tell.

Measurement is the part most teams skip. Hit rate is `cache_read_input_tokens / (cache_read_input_tokens + input_tokens)`, computed from fields the API already returns on every response, and anything below 60% on a production workload means there is headroom left. Logging those four usage counters per call site turns caching from a one-time change into a monitored property — which matters because the anti-patterns above are all regressions waiting to happen, introduced by an innocuous prompt edit weeks after the original work. Caching also composes with two other levers the source names: routing simple tasks to Haiku instead of Opus can move the same workload by up to 30x, and constraining output budgets caps the expensive half of the bill. Applied together, an unoptimized workload typically settles at 20-30% of its baseline. The same economics drive the session-hour math in [[claude-managed-agents-session-hour-pricing-2026]], where cache reads are priced separately from standard input on every current model.

## Key Concepts

- **Cache write vs cache read** — the first request carrying a marked prefix pays 1.25x (5-minute TTL) or 2x (1-hour TTL) base input to establish the entry; every subsequent request inside the window pays 0.1x.
- **Break-even reads** — 3 reads on the 5-minute TTL, 5 on the 1-hour TTL. Below that count the write premium costs more than the read discount saves.
- **Exact-bytes keying** — the cache key is the literal bytes of the cached span plus the model version. One changed character, one whitespace edit, or a model upgrade is a full miss.
- **Minimum cacheable prefix** — 1,024 tokens on Sonnet, 2,048 on Opus. Shorter prefixes are silently not cached; `cache_creation_input_tokens == 0` confirms it.
- **Cache hit rate** — `cache_read_input_tokens / (cache_read_input_tokens + input_tokens)`. Under 60% in production means unrealized savings.
- **`cache_control: {"type": "ephemeral", "ttl": "1h"}`** — the block-level marker placed on the last content element of the span to cache, in `system`, in a `messages` content array, or implicitly covering tool definitions.

## Relevance to AgentNexLiFy

Our widget chat is the exact shape of the measured support chatbot: a tenant-specific system prompt plus a knowledge-base context block plus a short user turn, repeated at volume. The tenant KB block is static across an entire conversation and usually across a whole day, which puts it squarely in 1-hour-TTL territory, and the conversation history belongs on the 5-minute TTL. The per-tenant structure is also the trap — anything that interpolates a tenant name, a business-hours string, or a "current time" into the prefix creates one cache namespace per tenant per request, which is the user-specific-content anti-pattern at multi-tenant scale. The correct construction puts the stable tenant KB in the cached span and the volatile per-request fields in the user message.

Two concrete follow-ups. First, instrument `cache_read_input_tokens` and `cache_creation_input_tokens` in `backend/services/llm_runtime.py` alongside the existing usage logging, so hit rate is visible per call site rather than inferred from the bill. Second, audit prefix length on the smaller call sites — lead qualification and structured extraction prompts may well sit under the 1,024-token Sonnet minimum, in which case they are paying full input price while appearing to be cached. The `PLAN_BASELINE_TOKENS` figures in `ai_usage_guard` were calibrated on uncached spend; a real hit rate on the `agent_os` widget path changes the unit economics under both paid plans.
