# Anthropic's August 2025 Infrastructure Postmortem — Three Overlapping Bugs That Degraded Claude

Between August 5 and September 16, 2025, three independent infrastructure bugs degraded response quality on Claude's first-party API, Bedrock, and Vertex AI. Anthropic's September 17, 2025 postmortem states explicitly that the company "never reduces model quality due to demand, time of day, or server load" — every reported regression traced to infrastructure, not deliberate throttling. The relevant fact for downstream consumers of Claude is not that bugs happened, but that Anthropic's standard evaluation process did not catch them, and that the resolution now includes continuous production evals and new deployment-time checks for out-of-distribution outputs. For AgentNexLiFy, which depends on Claude Sonnet 4.6 and Opus 4.7 for widget chat and managed agents, this changes how we should reason about silent-quality incidents and user-feedback loops.

The first bug — context-window routing — misrouted a fraction of Sonnet 4 requests to servers configured for the upcoming 1M context window. Initial blast radius was 0.8% of requests on August 5. A routine load-balancing change on August 29 unintentionally inflated routing error to a peak of 16% of Sonnet 4 requests on August 31. Because Anthropic's routing is sticky per session, a user whose first turn hit the bad server saw subsequent turns served by the same misconfigured pool — compounding the regression for power users. On Claude Code specifically, ~30% of users had at least one message routed incorrectly during the window. The fix was deployed September 4 and rollout completed September 18 on Bedrock; Vertex AI was affected at only 0.0004%.

The second bug — output corruption on TPU servers — stemmed from a runtime performance optimization deployed August 25. Token-generation code occasionally assigned high probability to tokens that should rarely appear given context, producing Thai or Chinese characters in English responses and obvious syntax errors in code. Opus 4.1 and Opus 4 were affected August 25–28; Sonnet 4 August 25–September 2. Third-party platforms (Bedrock, Vertex) were not affected. The postmortem commits to adding deployment-time detection tests for unexpected character outputs, which is the kind of cheap guardrail every high-stakes LLM pipeline should run ([[claude-code-best-practices]] frames verification criteria as the first lever for agentic reliability).

The third bug is the most technically interesting and the most relevant for teams running evals. An August 25 improvement to token selection triggered a latent XLA:TPU compiler bug in the approximate top-k operation. On TPUs, probability calculations are distributed across chips and sorting requires cross-chip coordination. Anthropic had previously patched a December 2024 symptom where temperature=0 sometimes dropped the most-probable token; that patch masked a deeper precision-mismatch problem caused by `xla_allow_excess_precision=true` promoting bf16 operations to fp32 inconsistently. The August 26 sampling rewrite removed the December workaround, exposing the underlying XLA approximate top-k bug which "sometimes returned completely wrong results, but only for certain batch sizes and model configurations." Haiku 3.5 was confirmed affected; Opus 3 likely; Sonnet 4 unreproducible but rolled back out of caution. Anthropic's fix: switch from approximate to exact top-k (efficiency delta was no longer prohibitive) and standardize additional ops on fp32.

Anthropic's own account of why detection took weeks is the most actionable part of the postmortem. Standard benchmarks did not capture the degradation because Claude often recovers from isolated mistakes. Internal privacy controls limited engineer access to user interactions unless explicitly reported, so reproducing bugs from noisy complaints was slow. Each bug produced different symptoms on different platforms at different rates, generating a confusing mix of reports that did not converge on a single cause. The company committed to (a) more sensitive evals that differentiate working vs broken implementations, (b) continuous production evals on real traffic rather than staging, and (c) privacy-preserving debugging tooling that lets engineers inspect problem interactions without violating data-handling guarantees. The `/bug` command in Claude Code and the thumbs-down button in Claude apps remain the sanctioned user feedback channel.

The ambient lesson for any team building on Claude is that silent degradation is real, infrequent, and hard to detect from the outside. User feedback telemetry (thumbs, `/bug`, rating) is load-bearing — not a nice-to-have. Internal evals that target behaviors your users actually care about (in our case: tenant-accurate answers, lead-capture correctness, appointment slot extraction) catch regressions that Anthropic's general evals will not. ## Key Concepts

- **Sticky routing** — Session-level server affinity where subsequent turns on a conversation are served by the same server pool as the first turn. Amplifies per-session impact of routing bugs: once misrouted, all follow-ups are misrouted.
- **xla_allow_excess_precision** — XLA compiler flag (default true) that permits optimization passes to convert bf16 operations to fp32 for the fp32-native TPU vector processor. The silent-promotion behavior caused cross-chip precision mismatches in probability calculations.
- **Approximate top-k** — Performance optimization that finds the top-k highest-probability tokens with accepted inaccuracy on lowest-probability tokens. The XLA bug caused it to sometimes return completely wrong results for specific batch sizes and model configurations, dropping the correct top token.
- **Canary deployment** — Anthropic's standard staged rollout where new infrastructure is deployed to small user groups first before broad rollout. The August 2025 incidents exposed that canary evals did not capture the user-observed degradation because Claude often recovers from isolated mistakes.
- **Privacy-preserving debugging** — Tooling that lets engineers reproduce production issues without broadly accessing user interaction data. Anthropic's current controls limit engineer access to non-reported interactions, which slowed investigation; the postmortem commits to building better tools here.

## Relevance to AgentNexLiFy

The direct implication is that we should build user-feedback telemetry into the widget and dashboard **before** we need it, not during an incident. A thumbs-up/thumbs-down on every widget reply, captured with the tenant ID and conversation ID, gives us the same signal Anthropic depends on. During a regression window like August 31 (16% of Sonnet 4 requests affected), our tenants would have seen degraded answers without us knowing — unless we had a rate-of-negative-feedback dashboard tuned for anomalous spikes. The second implication is that deployment-time checks for out-of-distribution outputs (non-English characters in English responses, syntax errors in code blocks, extremely short or extremely long responses) are cheap to add to our Claude wrappers in `backend/services/llm_runtime.py` and would catch entire classes of infrastructure-level corruption. Third: stick to first-party Anthropic API rather than Bedrock for the paths where we run the most volume, since the postmortem shows Anthropic-direct took the highest impact but also got fixes earliest. For multi-tenant latency-sensitive paths (widget chat), the trade-off still favors first-party.
