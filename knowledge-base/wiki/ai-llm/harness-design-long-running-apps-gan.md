# GAN-Inspired Three-Agent Harness — Planner, Generator, Evaluator for Long-Running Coding

Prithvi Rajasekaran's March 2026 Anthropic Engineering post documents a harness architecture that applies Generative Adversarial Network patterns to two adjacent problems: frontend design quality (subjective taste) and long-running autonomous full-stack coding (verifiable correctness). The core insight is that agents grading their own work skew positive — even when output quality is obviously mediocre — so separating generation from evaluation produces a better feedback loop than single-agent iteration. The post's central finding is that a three-agent system (planner, generator, evaluator) running on Opus 4.5 for 6 hours at $200 produced a functional retro game maker where a single-agent Opus 4.5 run for 20 minutes at $9 produced a broken prototype. The harness pattern is directly applicable to AgentNexLiFy's managed-agents architecture, issue-to-PR loop, and nightly commit review workflows.

The frontend-design experiment came first because the self-evaluation problem was most visible there. Claude's default taste "gravitates toward safe, predictable layouts that are technically functional but visually unremarkable." Rajasekaran's fix was four grading criteria — design quality, originality, craft, functionality — with design and originality weighted heavily because Claude already scored well on craft and functionality by default. The evaluator used Playwright MCP to actually interact with the live page (screenshotting, navigating, studying the implementation) before scoring each criterion. Runs used 5-15 iterations, stretched up to 4 hours wall-clock, and produced noticeable aesthetic shifts between iterations — including a notable case where iteration 10 scrapped a conventional dark-themed museum landing page and reimagined it as a 3D spatial experience with CSS-perspective rooms and doorway-based navigation. The key observation: evaluator criteria wording materially shaped output character. Phrases like "the best designs are museum quality" pushed designs toward specific visual convergence, suggesting prompt phrasing in the evaluator prompt is itself a design choice.

The three-agent architecture for full-stack coding extends the frontend experiment. Planner takes a 1-4 sentence prompt and expands it into a full product spec, deliberately staying at product-context and high-level technical level rather than detailed implementation — because errors in detailed spec cascade into downstream implementation failures. The planner is instructed to find opportunities to weave AI features into specs, which becomes a differentiator: the generated retro game maker included a built-in Claude integration for generating sprites, levels, and game elements through natural language. Generator implements one feature at a time in sprints, using a React/Vite/FastAPI/SQLite stack (later PostgreSQL), with git for version control, self-evaluating at sprint boundaries before handing to QA. Evaluator uses Playwright MCP to click through the running app like a user would, testing UI features, API endpoints, and database state, grading against sprint-specific criteria with hard thresholds — if any criterion falls below threshold, the sprint fails and the generator gets detailed feedback.

The sprint contract is the most transferable pattern. Before each sprint, generator and evaluator negotiate a file-based contract defining what "done" looks like for that chunk — the generator proposes what it will build and how success will be verified, the evaluator reviews that proposal, they iterate until agreement, then the generator builds against the agreed contract. Communication happens via files: one agent writes, the other reads and responds either in the same file or a new file. This is the same coordination pattern as our `.claude/agent-comms/` advisor-brief flow in [[claude-opus-4-7-release]]'s advisor-executor architecture. Sprint 3 of the retro-game-maker run had 27 acceptance criteria covering the level editor alone; evaluator findings were specific enough to act on without investigation ("Delete key handler at LevelEditor.tsx:892 requires both selection and selectedEntityId to be set, but clicking an entity only sets selectedEntityId. Condition should be selection || (selectedEntityId && activeLayer === 'entity')").

Tuning the evaluator was the hardest part. Out of the box Claude is a poor QA agent — it identifies legitimate issues, then talks itself into deciding they're not a big deal and approves the work anyway. It tests superficially rather than probing edge cases. Rajasekaran's tuning loop: read the evaluator's logs, find examples where its judgment diverged from his, update the QA prompt to solve for those issues. Several rounds. Even after tuning, the evaluator missed small layout issues, unintuitive interactions, and bugs in deeply-nested features it didn't exercise thoroughly. Separating evaluator from generator does not eliminate LLM-to-LLM leniency on its own; tuning the evaluator to be skeptical is the load-bearing work. This matters for AgentNexLiFy's [[claude-code-best-practices]] verification-criteria discipline and our own code-reviewer agent tuning.

The v2 harness iteration is where the post reveals its deepest principle: every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress-testing because they may be incorrect or go stale as models improve. When Opus 4.6 released, Rajasekaran removed the sprint construct entirely — Opus 4.6's improved long-context retrieval and reduced context-anxiety meant the model could handle the job without sprint decomposition. He kept planner and evaluator because each still added obvious value: without planner, generator under-scoped (starting to build without speccing first); evaluator continued to catch edge-case issues at the boundary of the model's reliable solo performance. The v2 DAW build ran 3h50m at $124.70: planner 4.7min/$0.46, Build Round 1 2h7min/$71.08, QA Round 1 8.8min/$3.24, two more build-QA rounds for refinement. QA kept catching real gaps — stub audio recording, missing clip resize, numeric-only effect visualizations where graphical was specified.

The practical implication is that evaluator value scales with how far the task sits beyond the model's solo reliability. On Opus 4.5 the boundary was close — builds were at the edge of what the generator could do well alone, and evaluator caught meaningful issues across the build. On Opus 4.6 the boundary moved outward, so tasks within the new reliability zone don't benefit from the evaluator overhead. This is not a fixed yes-or-no architecture decision; it is a continuous cost-benefit calculation that shifts with every model release. [[effective-harnesses-long-running-agents]] and [[effective-context-engineering]] provide the foundational patterns; this post shows how those patterns evolve under generator-evaluator separation.

## Key Concepts

- **Generator-evaluator separation (GAN pattern)** — Architectural choice where one agent produces output and a distinct agent grades it against criteria. Inspired by Generative Adversarial Networks. Useful because agents grading their own work skew positive; separation creates something concrete for the generator to iterate against. Does not eliminate LLM leniency on its own — evaluator must be tuned for skepticism.
- **Sprint contract** — File-based agreement between generator and evaluator before code is written, defining what "done" looks like for a chunk of work. Bridges high-level product spec and testable implementation. Generator proposes, evaluator reviews, iterate until agreement, then generator builds against the agreed contract.
- **Context reset vs compaction** — Context reset clears the conversation entirely and starts a fresh agent with a structured handoff; compaction summarizes earlier parts in place so the same agent continues on shortened history. Context resets prevent context anxiety (agents wrapping up prematurely as they approach perceived context limits); compaction does not. Opus 4.6 largely eliminated the need for context resets that Opus 4.5 required.
- **Context anxiety** — Failure mode where a model wraps up work prematurely as it approaches what it believes is its context limit. Documented on Sonnet 4.5 strongly enough that compaction alone was insufficient; required context resets. Reduced on Opus 4.6.
- **Load-bearing harness component** — A harness piece whose removal measurably degrades output quality. Distinguishes load-bearing components from scaffolding that once made sense but now adds cost without lift. Methodical one-at-a-time removal reveals which is which; simpler harnesses are better than complex ones when simpler works.
- **Test-time compute harness** — Infrastructure that gives a model extended deliberation time, repeated iteration, and tool access across many hours. Anthropic's internal test-time compute harness is what enabled Opus 4.5 to defeat the v2 performance engineering take-home (see [[ai-resistant-technical-evaluations]]).

## Relevance to AgentNexLiFy

The three-agent pattern maps directly onto our managed-agents architecture, nightly commit review, and issue-to-PR loop. Current state: compound-engineering skill runs Brainstorm → Plan → Execute → Review → VerticalCheck sequentially; issue-to-PR loop uses Haiku classify + Sonnet implement + feedback loop. The Rajasekaran pattern suggests we should (1) add a dedicated evaluator agent for nightly commit review that uses our widget or admin UI via Playwright MCP to verify fix claims, not just read diffs; (2) introduce sprint-contract negotiation in issue-to-PR loop so the generator's initial implementation proposal is reviewed by an evaluator before any code is written — this front-loads alignment and reduces wasted implementation cycles; (3) tune our code-reviewer agent (`.claude/agents/code-reviewer.md`) to be skeptical rather than default-approving, using the same read-logs-update-prompt tuning loop Rajasekaran describes. The cost model ($124-200 per multi-hour run) is too expensive for per-tenant widget flows but fits nightly batch work and high-stakes feature PRs. The load-bearing-component principle argues against adding evaluator overhead to tasks the model handles reliably alone; we should benchmark solo-Sonnet-4.6 performance on typical issue-to-PR tasks before committing to evaluator tuning spend.
