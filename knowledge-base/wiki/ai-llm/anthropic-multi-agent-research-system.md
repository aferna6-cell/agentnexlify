# Anthropic's Multi-Agent Research System — Orchestrator-Worker Architecture and 90.2% Single-Agent Lift

Anthropic's engineering writeup on Claude's Research feature is the most concrete public look at production multi-agent architecture from a frontier lab. The headline result: Claude Opus 4 as lead orchestrator with Claude Sonnet 4 subagents in parallel beat single-agent Claude Opus 4 by 90.2% on Anthropic's internal research evaluation. Token analysis on the BrowseComp benchmark showed three factors explaining 95% of performance variance — token usage alone accounting for 80%, with tool-call count and model choice splitting the remainder. The architecture validates the thesis that multi-agent systems are primarily a way to add parallel context capacity, not a way to add reasoning depth, and that they only pay for themselves on tasks where the value justifies a 15x token-cost multiplier over chat.

The architectural shape is orchestrator-worker. A lead agent receives the query, develops a strategy, and spawns 3–5 subagents in parallel. Each subagent gets an objective, an output format, tool guidance, and explicit task boundaries — the post is emphatic that vague instructions produce duplicate work and gaps in coverage, citing an early failure where one subagent investigated the 2021 automotive chip shortage while two others duplicated work on the 2025 supply chain. Subagents run their own search loops, call 3+ tools in parallel themselves, then return condensed findings. The lead agent compiles, decides whether more depth is needed, and either spawns new subagents or finalizes. This dual-level parallelism — lead spawns parallel subagents, subagents run parallel tool calls — cut research time by up to 90% on complex queries.

The economics flip the framing of when multi-agent makes sense. Anthropic measured agent token consumption at roughly 4× chat for single agents and 15× chat for multi-agent. Single-agent runs are already expensive; multi-agent compounds the cost. The constraint this places on viable use cases is sharp: the task value must justify the 15x multiplier, and the task must be genuinely parallelizable. Research is a textbook fit because subqueries are independent. Coding usually isn't, because most tasks have sequential dependencies and require shared context that multi-agent fragmentation breaks. Anthropic explicitly warns that "LLM agents are not yet great at coordinating and delegating to other agents in real time," which rules out dynamic asynchronous coordination patterns at current capability levels.

Prompt engineering is the primary lever for steering multi-agent behavior. Seven heuristics from the post define the operational discipline: think like the agent (build mental simulations and watch step-by-step), teach the orchestrator how to delegate (objective + format + tool guidance + boundaries), scale effort to query complexity (1 agent / 3-10 calls for facts, 2-4 agents / 10-15 calls each for comparisons, 10+ agents for deep research), tool design and selection are critical, let agents improve themselves (Claude 4 was used as its own prompt engineer, producing 40% task-completion-time reductions), start wide then narrow down, and guide the thinking process via extended thinking as a controllable scratchpad. The subagent-improving-tools loop is reusable across any MCP-tool stack — the methodology connects directly to [[anthropic-writing-tools-for-agents]].

Evaluation philosophy diverges from traditional software testing. Multi-agent runs are non-deterministic, with valid paths fanning out from any starting point. Path-based evaluation breaks; outcome-based evaluation works. Anthropic recommends starting with ~20 representative test cases (early changes have huge effect sizes — a prompt tweak that boosts success from 30% to 80% is visible in 20 cases), then scaling LLM-as-judge with a single judge model outputting 0.0-1.0 + pass/fail across factual accuracy, citation accuracy, completeness, source quality, and tool efficiency. Human evaluation catches what automation misses: in their case, agents systematically chose SEO-optimized content farms over higher-quality but lower-ranked academic PDFs and personal blogs until the prompt was updated with source-quality heuristics.

Production reliability raises its own class of problems. Agents are stateful and long-running, so errors compound — a minor system failure mid-loop can cascade into total task failure. Restarting from scratch is expensive and frustrating, so Anthropic built durable execution with checkpoint-resume semantics. The deployment story is equally distinct: agents are running continuously when new code ships, so traditional all-at-once rollouts would break in-flight runs. They use rainbow deployments — gradually shifting traffic from old to new versions while keeping both running — to avoid disrupting active agents. Synchronous lead-to-subagent execution remains a bottleneck (the lead can't steer subagents mid-search and must wait on the slowest subagent to finish), but they note that asynchronous execution adds enough state-consistency complexity that it's deferred until model capability justifies the engineering investment.

Three appendix patterns deserve their own attention. End-state evaluation — judging the final state of the world rather than each intermediate step — works for state-mutating agents where multiple paths reach the same goal. Long-horizon conversation management uses external memory plus fresh-subagent handoffs to bypass context-window limits, mirroring patterns in [[memory-for-ai-agents-context-engineering]]. The "subagent output to filesystem" pattern is particularly powerful: instead of subagents passing all results through the lead agent (which loses fidelity in the "game of telephone" and burns tokens), they write artifacts directly to a filesystem and pass lightweight references back. The pattern matches how skilled human researchers work — delegate, deliver an artifact, review the artifact, not the path.

## Key Concepts

- **Orchestrator-worker pattern** — One coordinating lead agent decomposes the task and spawns parallel specialized subagents. Subagents return condensed findings; lead compiles. Distinct from sequential pipelines where each step blocks the next.
- **Token-cost multiplier** — Multi-agent systems consume ~15x chat tokens; single agents ~4x. The ratio constrains which tasks are economically viable to run multi-agent.
- **Rainbow deployment** — Gradual traffic shift from old to new code versions while keeping both running, so long-running agents complete their loop on whichever version they started on.
- **End-state evaluation** — Judging an agent's final output state rather than its specific path. Necessary because multi-agent runs reach goals via diverse non-deterministic paths.
- **Game of telephone** — Information loss when subagent results pass through the lead agent's context before reaching the user. Mitigated by writing artifacts directly to a filesystem with the lead receiving only references.
- **Effort-scaling rules** — Explicit prompts that scale tool-call budget to query complexity (e.g., 1 agent / 3-10 calls for fact-finding, 10+ agents for deep research) to prevent overinvestment on simple queries.

## Relevance to AgentNexLiFy

Three implications for our roadmap. First, the 15x token-cost multiplier is a hard guard against over-using multi-agent patterns in widget chat — those calls are latency-sensitive and price-sensitive, and most tenant workflows are inherently sequential (qualify → book → confirm). Multi-agent belongs in the "research" surface where we'd want it: tenant onboarding deep-dives (industry research, competitor pricing, KB seeding), nightly cross-tenant audit runs, and any future "research mode" feature that justifies the cost. Second, the orchestrator-worker pattern slot maps cleanly onto our existing Opus-advisor / Sonnet-executor split — the upgrade path is letting the advisor spawn parallel subagents during research-heavy advisor passes, mediated by the rules in `.claude/rules/parallel-approaches.md`. Third, the rainbow-deployment requirement is a sleeper concern: as we move automation jobs to longer-running loops (issue-to-PR, nightly commit review, KB autopopulate), naive deploys will start interrupting active agents. The fix is staged rollouts that respect in-flight state — worth filing as a backlog item before the count of long-running agents grows, not after.
