# Claude Code April-23 Postmortem — Three Bugs That Faked Model Degradation

Anthropic published a postmortem on 2026-04-24 explaining the "Claude got dumber" reports that ran through March and April. The cause was three separate, independently-shipped changes to **Claude Code** (and downstream the Claude Agent SDK and Claude Cowork), not the Claude API or inference layer. Each change touched a different slice of traffic on a different schedule, so the aggregate effect looked like broad inconsistent degradation. All three were resolved as of April 20 in v2.1.116. Anthropic is resetting usage limits for all subscribers as of April 23 and is changing internal eval and rollout discipline to prevent the pattern from recurring. For any project running on Claude Code (this repo included), the postmortem is also a maintenance log: anyone who diagnosed a "regression" between March 4 and April 20 should re-examine whether their workaround is still needed.

The first bug was a **default reasoning-effort downgrade**. When Opus 4.6 launched in Claude Code in February, default effort was `high`. Users reported that high mode could think long enough to make the UI appear frozen. On March 4 the default was lowered to `medium` — slightly lower intelligence with significantly less latency on most tasks, fewer long-tail freezes, and better usage-limit utilization in evals. Users disagreed; they retained the medium default rather than switching back manually, and reported Claude Code felt less intelligent. Reversed April 7. Default is now `xhigh` for Opus 4.7 and `high` for everything else. The lesson Anthropic states is that the right tradeoff was to default to higher intelligence and let users opt into lower effort for simple tasks, not the inverse. This aligns with our project's `effortLevel: "high"` setting in `.claude/settings.json` and our [[claude-opus-4-7-release]] xhigh-effort default.

The second bug was a **caching optimization that silently dropped prior reasoning**. On March 26, Anthropic shipped a change intended to prune old thinking blocks from sessions idle for over an hour, using the `clear_thinking_20251015` API header with `keep:1`. The design was sound: a stale session is a cache miss anyway, so dropping old reasoning before the resume request reduces uncached input cost. The implementation had a bug — instead of clearing once on resume, it kept clearing on every turn for the rest of the session. Compounding effect: a follow-up message during a tool call started a new turn under the broken flag, so even the current turn's reasoning was discarded. Symptoms users observed were forgetfulness, repetition, odd tool choices, and faster-than-expected usage-limit drain (the requests also missed cache because the prefix kept changing). Two unrelated experiments suppressed the bug in internal tests, which is why it survived multiple human and automated reviews and dogfooding. It took over a week to root-cause. Notably, when Anthropic back-tested **Code Review** with Opus 4.7 against the offending PRs, Opus 4.7 found the bug and Opus 4.6 didn't — so they're now landing additional repository context in Code Review to harden the next loop. Fixed April 10 in v2.1.101.

The third bug was a **system-prompt line added on April 16 to reduce verbosity** when Opus 4.7 launched. Opus 4.7 is more verbose than 4.6 by training; Anthropic uses model training, prompt engineering, and product UX in combination to manage that. One specific addition to the system prompt produced an outsized hit on coding intelligence in Claude Code that the pre-launch eval suite didn't catch. Post-incident ablations (removing lines one at a time and re-running a broader eval set) showed a 3% drop on both Opus 4.6 and 4.7. Reverted in the April 20 release. The takeaway here is that small prompt changes can have outsized intelligence effects that narrow eval suites miss — exactly the failure mode our `.claude/rules/opus-4-7-prompting.md` `§3 (delete progress scaffolding)` and `§2 (positive examples beat negative rules)` are trying to anticipate on the user side.

The going-forward changes Anthropic announced are operationally interesting. They will: ensure more internal staff use the exact public build of Claude Code (not the dogfood variant); ship the improved Code Review tool externally; run a broad per-model eval suite for every system-prompt change; continue ablations to understand each line's impact; add tighter review tooling for prompt changes; gate model-specific prompt changes by `CLAUDE.md` to the targeted model only; and add soak periods, broader eval suites, and gradual rollouts for any change with potential intelligence tradeoffs. They also stood up `@ClaudeDevs` on X to explain product decisions and are mirroring updates in centralized GitHub threads. For our project, the explicit adoption of model-gated prompt changes via `CLAUDE.md` validates the path-scoped rules pattern documented in [[claude-code-best-practices]].

The postmortem also implicitly answers a question this project hit during the same window. Our `.claude/rules/claude-version-pin.md` pinned `claude-code@2.1.98` after community-reported phantom-token inflation in v2.1.100+. The bug fixes shipped in v2.1.101 (March 26 cache fix), v2.1.116 (April 20 verbosity revert), and the April 7 effort default revert. The version-pin sunset criteria already includes "Anthropic changelog explicitly notes fix for cache_creation inflation" — this postmortem documents the cache-side bug, which is plausibly the same root cause as the phantom tokens since cache misses on every turn would inflate `cache_creation_input_tokens`. Re-evaluate the pin after a full week of independent telemetry on v2.1.116 or later.

## Key Concepts

- **Reasoning effort levels** — Discrete points on the test-time-compute curve (medium / high / xhigh / max) exposed in Claude Code via `/effort`. Higher = more thinking, longer latency, more output tokens, generally better quality.
- **`clear_thinking_20251015` API header** — Anthropic API directive that lets a client trim earlier thinking blocks from a request to reduce cache-miss cost on resume; `keep:N` keeps the last N. The April 10 fix corrected the Claude Code client's misuse of this header.
- **Prompt caching cache-miss inflation** — When a prompt prefix changes turn-to-turn, every request becomes a cache miss; `cache_creation_input_tokens` rise even though wall-time output looks unchanged. Cause of "usage drains faster than expected" reports.
- **Ablation testing** — Removing one line of a prompt at a time and rerunning the eval suite to attribute intelligence delta to each line. Used post-incident to identify the verbosity-line regression.
- **Default effort downgrade** — The pattern where a vendor optimizes for latency and usage-limit headroom by lowering default reasoning, and discovers users prefer the slower, smarter default. Reversed in this incident.
- **Continuous production evals** — Anthropic's stated future state: per-model eval suites run on every system-prompt change, with soak windows and gradual rollout. Mirrors the eval-driven development pattern in `.claude/skills/eval-harness/`.

## Relevance to AgentNexLiFy

Three concrete actions for this project. (1) **Re-evaluate the v2.1.98 pin in `.claude/rules/claude-version-pin.md`.** The cache-miss bug fixed in v2.1.101 is a plausible cause of the phantom-token inflation that motivated the pin. Run a one-week telemetry comparison on v2.1.116 vs 2.1.98, sunset the pin if `cache_creation_input_tokens` parity holds. (2) **Audit any workarounds or `bug-patterns.md` entries written between March 4 and April 20.** If a workaround was added because Claude Code "felt forgetful" or "couldn't follow long sessions," the underlying cause was the cache-pruning bug, not a real model regression — remove the workaround and re-test. (3) **Validate the path-scoped `CLAUDE.md` pattern in `.claude/rules/path-scoped-rules.md`.** Anthropic explicitly cited model-specific guidance gated through `CLAUDE.md` as the going-forward fix; our existing path-scoping for `python-fastapi.md`, `widget-rules.md`, and `schema-discipline.md` is the correct shape and worth keeping. The broader operational lesson — that small prompt changes can produce 3% intelligence regressions that a narrow eval suite misses — is the same logic that justifies our `.claude/skills/eval-harness/` and the recommendation to run ablations whenever we touch system prompts in `backend/services/llm_runtime.py`.
