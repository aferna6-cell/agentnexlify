# Effective Context Engineering for AI Agents — Anthropic's Framework

Anthropic's context-engineering post formalizes a shift the field has been making for two years: from writing clever prompts to curating the full token state an agent operates under. The core claim is mechanical — the transformer architecture creates n² pairwise relationships across n tokens, so as context grows the model's attention budget per token thins, and research on context rot shows recall accuracy degrades measurably past certain token counts. Context therefore must be treated as a finite resource with diminishing marginal returns, which makes "find the smallest possible set of high-signal tokens that maximize likelihood of desired outcome" the single guiding principle across system prompts, tools, examples, message history, and retrieved data. This reframing is the lens behind [[effective-harnesses-long-running-agents]], [[memory-for-ai-agents-context-engineering]], and Claude Code's CLAUDE.md+glob+grep hybrid design.

The prompt-engineering-to-context-engineering progression is iterative, not a one-time write. Prompt engineering optimized a static system prompt for one-shot tasks; context engineering curates what flows into the window on every turn of a multi-turn agent. The curation happens at each decision point about what to pass next. Anthropic recommends system prompts that hit the right "altitude" — specific enough to guide behavior, flexible enough to give the model strong heuristics rather than brittle if-else trees. Failure modes at both extremes: hardcoded brittle logic that breaks on edge cases, and vague high-level guidance that assumes shared context the model doesn't have. The Goldilocks zone is reached by starting with a minimal prompt on the best model, observing failures, and adding targeted instructions or examples to address real failure modes — not hypothetical ones.

Tool design gets treated as a first-class context engineering concern. Tools define the contract between the agent and its action space, so they must return token-efficient outputs and encourage efficient agent behavior. The most common failure Anthropic sees is bloated tool sets with too much functional overlap and ambiguous decision points — if a human engineer can't tell which of two tools applies in a given scenario, neither can the agent. Tool inputs should be descriptive and unambiguous; tools should be self-contained, robust to error, and have minimal overlap. Few-shot examples should be curated (diverse, canonical) not exhaustive (laundry list of edge cases stuffed in the prompt). The cumulative rule: be thoughtful, keep context informative yet tight.

Just-in-time retrieval replaces pre-inference embedding-based context stuffing as the field's dominant pattern. Rather than pre-processing all potentially-relevant data and loading it up front, the just-in-time approach has the agent maintain lightweight identifiers — file paths, stored queries, web links — and load data into context dynamically via tools at the moment it's needed. Claude Code's architecture is the canonical example: CLAUDE.md loads naively up front, but glob, grep, bash head/tail, and file reads pull exact content just when needed, avoiding stale indices and complex syntax trees. The metadata of these references (file names, folder paths, naming conventions, timestamps) carries implicit signal — a `test_utils.py` in `tests/` means something different than the same filename in `src/core_logic/`. Progressive disclosure through exploration lets agents build understanding layer by layer while keeping working memory focused. The tradeoff is speed — runtime exploration is slower than pre-computed retrieval — so hybrid strategies (some pre-loaded context plus autonomous exploration) often win on balance. The decision boundary depends on task characteristics: static domains (legal, finance) benefit from more pre-loading; dynamic domains (code, operations) benefit from more just-in-time.

For long-horizon tasks that exceed the context window, three techniques address context pollution directly. Compaction — summarizing a conversation nearing the window limit and reinitializing with the summary — serves as the first lever and is built into Claude Code, which preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs. The art is tuning what to keep versus discard: start by maximizing recall (capture every relevant item), then iterate for precision (eliminate redundancy). Tool result clearing — dropping raw tool outputs once the conclusions are integrated — is the lightest-touch form. Structured note-taking (agentic memory) has the agent regularly persist notes outside the context window and pull them back later, which is how [Claude playing Pokémon](https://www.twitch.tv/claudeplayspokemon) maintains strategies across thousands of game steps without context resets destroying progress. Anthropic released a file-based memory tool in public beta with Sonnet 4.5 for exactly this pattern — same concept behind AgentNexLiFy's memory system at `~/.claude/projects/-home-aidan-agentnexlify/memory/`. Sub-agent architectures handle the final lever: specialized sub-agents get clean context windows for focused tasks and return distilled summaries (1,000-2,000 tokens) to the main orchestrator, preserving separation of concerns and scaling parallel exploration. This is the pattern [[anthropic-managed-agents-architecture]] productizes and that AgentNexLiFy uses for [[claude-opus-4-7-release]]-advisor + Sonnet-executor pipelines.

The choice between compaction, note-taking, and sub-agents depends on task shape. Compaction fits conversational flow with extensive back-and-forth. Note-taking fits iterative development with clear milestones. Multi-agent fits complex research and analysis where parallel exploration pays dividends. Even as context windows grow, context pollution and relevance concerns persist, so these techniques are not going away — they're the foundation of long-horizon agent reliability. The closing guidance: "do the simplest thing that works" — as models improve, less prescriptive engineering is needed, and intelligent models benefit from being allowed to act intelligently with less curation.

## Key Concepts

- **Context engineering** — The set of strategies for curating and maintaining the optimal token set during LLM inference, covering system prompts, tools, examples, message history, MCP, retrieved data. Iterative evolution of prompt engineering for multi-turn agents.
- **Attention budget** — Finite per-token attention capacity in a transformer; grows worse with longer context because of n² pairwise attention and training-distribution bias toward shorter sequences.
- **Context rot** — Measurable decline in recall accuracy as context tokens increase, observed across all models with varying severity. Motivates treating context as finite resource with diminishing returns.
- **Right altitude** — Goldilocks zone for system prompts: specific enough to guide behavior, flexible enough to not be brittle. Failure at both extremes — hardcoded if-else logic versus vague high-level guidance.
- **Just-in-time retrieval** — Agent maintains lightweight identifiers (paths, queries, links) and loads data at runtime via tools, rather than pre-loading all potentially-relevant data. Mirrors human cognition; canonical example is Claude Code's glob/grep/file-read pattern.
- **Progressive disclosure** — Incrementally revealing context through exploration; file metadata (names, paths, sizes, timestamps) provides implicit signal that lets agents assemble understanding layer by layer.
- **Compaction** — Summarizing context approaching the window limit and reinitializing with the summary plus the last N files/tool results. First-line context-engineering technique for long-horizon tasks.
- **Tool result clearing** — Lightest-touch compaction: dropping raw tool outputs once conclusions are integrated. Feature launched on Claude Developer Platform.
- **Structured note-taking** — Agent persists notes to external storage (file system, database) and retrieves them later. Same concept as [[memory-for-ai-agents-context-engineering]]'s file-based memory tools.
- **Sub-agent architecture** — Specialized sub-agents get clean context windows, return distilled summaries (1k-2k tokens). Clear separation of concerns; scales parallel exploration.

## Relevance to AgentNexLiFy

Context engineering is the framing we should use for the entire AgentNexLiFy backend agent stack, not just for Claude Code sessions. The widget chat flow has an obvious attention budget problem — system prompt plus tenant KB plus conversation history grows linearly per message, and at high volume tenants we're paying for both dollars (input tokens) and quality (context rot). The just-in-time retrieval pattern maps directly onto how `backend/services/chat_service.py` should load tenant KB content: maintain lightweight identifiers (KB article slugs with embeddings via [[pgvector-postgres-vector-search]]) and load full articles only when the query vector hits, rather than stuffing the top-3 articles into every prompt. Compaction should be the fallback when conversations exceed ~8k tokens: summarize the resolved portion of the conversation, keep the last 3-5 turns verbatim, and prepend the summary. Structured note-taking maps onto per-tenant persistent memory — we already have `memory/` for Claude Code sessions but not for tenant widget conversations, which is a gap. Sub-agent architecture maps onto the [[anthropic-managed-agents-architecture]] Managed Agents pattern already wired for Lead Qualifier and Document Drafter. The single highest-ROI implementation would be adding compaction + KB just-in-time retrieval to `chat_service.py` — measured impact would be 30-50% input token reduction per conversation based on Anthropic's compaction case studies, plus quality lift on conversations over 10 turns.
